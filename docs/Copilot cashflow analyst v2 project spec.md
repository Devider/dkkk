# Копилот кредитного аналитика: агент v2 — проектная спецификация

Oct 23, 2026 · @Aleksei

## 1. Контекст и цели

Агентный цикл сервиса `aigw-rest-service` переносится с самописного графа LangGraph (`api/v1/main_graph.py`) на LangChain `create_agent` с явно собранным стеком middleware. Индекс модели, смысловой слой, движок пересчёта и логика инструментов остаются без изменений.

**Цель.** Агент принимает многосоставный запрос кредитного аналитика, раскладывает его на шаги и строит план вызова инструментов. При неудаче он корректирует план, доводит его до завершения и выдаёт результат языком экономики. Предметные сценарии сложных расчётов описываются скиллами (skills) и подключаются без правки кода агента.

Документ — единый источник требований для всей реализации. Каждая story в разделе 15 ссылается на ID требований из разделов 4 и 5 и на решения из раздела 6. Story нарезается на изменения OpenSpec (`openspec/changes/<story-id>/`). Мастер-спеки `openspec/specs/<capability>/spec.md` создаются по мере реализации: требование попадает туда как `Requirement` + `Scenario` из дельты своей story при её архивации, а не заранее. Целевые числа в документе — предложение, их нужно подтвердить.

### Текущее состояние

| Аспект | Сейчас | Чем мешает |
| --- | --- | --- |
| Цикл | Свой граф `extract_excel_data → orchestrator ⇄ tool_executor → synthesizer`, ReAct на `bind_tools` | Повторы, лимиты, дедупликация и логи зашиты в узлы. Новая сквозная функция требует правки графа |
| План | Нет. Жёсткий лимит — 4 итерации оркестратора | Составной запрос обрывается на середине, не видно, что сделано и что нет |
| Инструменты для LLM | 2 обёртки (`analyze_model_inputs_for_target`, `analyze_excel_model`) с одним аргументом `reformulated_query` | Сопоставление имён (\~55 % точности на параметр) спрятано внутри. Агент не видит промаха и не может его исправить |
| Ошибки | Статусы OK / WARNING / INFO / ERROR в свободном тексте | Нет кодов. Агент не отличает «повторить», «перепланировать» и «спросить» |
| Знания домена | Внутри `ORCHESTRATOR_PROMPT` и `SYNTHESIZER_PROMPT` | Промпт растёт с каждым сценарием, знания нельзя подключить точечно или проверить отдельно |
| Ответ | Отдельный узел `synthesizer` | Числа в ответе не сверяются с результатами расчётов |

### Цели v2

| ID | Цель | Мера успеха (предложение) |
| --- | --- | --- |
| G1 | Составной запрос решается целиком | ≥ 80 % ходов eval-набора с доведённым планом |
| G2 | Ошибка шага не обрывает ход | ≥ 70 % ходов с ошибкой инструмента завершены корректным ответом |
| G3 | Ответ — вывод аналитика, а не пересказ таблицы | Оценка аналитика ≥ 4 из 5 на выборке; 100 % чисел ответа найдены в результатах |
| G4 | Новый сценарий без правки кода агента | Новый skill подключается только файлами в `api/v2/skills/` |
| G5 | Не хуже текущего агента на одиночных запросах | Per-param accuracy и время ответа на текущем наборе Methanex не хуже v1 |

## 2. Границы

Меняются агентный рантайм, адаптер инструментов, промпты и наблюдаемость. Всё, что считает числа или сопоставляет имена, переиспользуется как есть.

**В рамках:**

- сервис FastAPI с несколькими пользователями (`x-user-id`), развёртывание в Docker;
- модели Excel, пересчёт через LibreOffice (UNO);
- LLM — только GigaChat: по api\_key (`GIGACHAT_CREDENTIALS`) и по сертификатам во внутреннем контуре, плюс скриптовая модель для тестов;
- внешний контракт `/api/v1/upload` и `/api/v1/invoke-agent` сохраняется.

**Не входит в задачу:**

- переписывание расчётной логики и повышение точности самого матчера имён (эмбеддинги, новый алгоритм) — отдельная инициатива;
- потоковый (SSE) интерфейс и собственный UI;
- заполнение `generated/agent_output.xlsx` результатами;
- долговременный checkpointer (Pangolin/Postgres) — допускается позже за тем же интерфейсом;
- внешний трейсинг за пределами контура (LangSmith и аналоги).

### Неизменяемые компоненты

Правило для всех строк таблицы: тела функций не правятся. Разрешено только менять место и способ вызова (оборачивать, выносить в отдельный инструмент, кэшировать).

| Смысловой слой | `subagents/analyzer.py:AnalyzerSubAgent`, `tools.py:find_matching_cell`, `find_matching_outputs`, `normalize_text`, `russian_stemmer.py`, глоссарий, промпты `ift_analizer`, `ema_analizer`, `lookup_more` | Сопоставляет слова пользователя с каноническими именами, извлекает цели, годы, диапазоны, переводит проценты | Вызывается отдельным инструментом `resolve_terms` (ADR-4) |

## 3. Глоссарий

| Термин | Значение |
| --- | --- |
| Ход (turn) | Один вызов `/invoke-agent`: сообщение пользователя → цикл агента → финальный ответ |
| Сессия (thread) | Последовательность ходов с одним `thread_id = "{x-user-id}:{x-session-id}"` |
| Индекс модели | Каталог входов и выходов загруженной книги с ID, каноническими именами, единицами и адресами по годам |
| Смысловой слой | Сопоставление слов аналитика («copper», «цена меди») с каноническими именами индекса и извлечение параметров запроса |
| Расчёт | Пересчёт книги в LibreOffice с изменёнными входами. Исходный файл не меняется |
| Подбор под цель (IFT) | Поиск значений входов, при которых выход достигает цели в заданном году (`analyze_model_inputs_for_target`) |
| Сценарная сетка (EMA) | Пересчёт выходов по диапазонам входов с шагом (`analyze_excel_model`) |
| План | Список шагов хода в состоянии агента (`todos`), каждый со статусом |
| Шаг | Пункт плана: одно действие аналитика (найти показатель, посчитать сценарии, сделать вывод). Может требовать нескольких вызовов |
| Middleware | Расширение `create_agent`, встроенное в цикл через хуки `before_agent`, `before_model`, `wrap_model_call`, `after_model`, `wrap_tool_call`, `after_agent` |
| Skill | Папка с `SKILL.md`: когда применять, шаблон плана, правила интерпретации, открываемые инструменты |
| Конверт результата | Единый формат ответа любого инструмента: `status`, `result`, `notes`, `hint`, `ref` или `error`, `code`, `hint` |
| Выжимка хода | Компактная запись итогов хода (найденные показатели, цифры, ссылки на результаты) для следующих ходов |
| Ковенанта | Порог финансового показателя из кредитного договора (например, DSCR ≥ 1,2; Debt/EBITDA ≤ 3,5) |

## 4. Функциональные требования

Решение обязано выполнять 20 функциональных требований в шести группах. Каждое переносится в OpenSpec как `Requirement`, а критерий приёмки — как `Scenario` (WHEN / THEN).

### Приём и понимание запроса

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| FR-1 | Ход начинается с загрузки книги пользователя из store и индекса модели из реестра (строится при загрузке файла). Нет файла — понятный ответ без вызова LLM | Запрос без `/upload` получает ответ «загрузите модель», в журнале 0 вызовов LLM |
| FR-2 | Ограничения: только русский и английский, только анализ загруженной модели. Язык проверяется до цикла без LLM, тема — моделью по правилам системного промпта. Нарушение — фиксированный отказ без вызова инструментов | Запрос на немецком и запрос «напиши код» получают отказ, ни одного вызова инструмента |
| FR-3 | Декомпозиция. В режиме плана первый вызов модели создаёт план из 1–7 шагов. Каждое действие из запроса и каждый нужный промежуточный шаг (например, базовое значение для относительного диапазона) попадает в план | Тест middleware: первый tool call хода, не считая чтения skill (`read_file /skills/...`), — `write_todos`. Eval: покрытие действий запроса планом ≥ 90 % |
| FR-4 | Режим без плана для вопросов без расчёта (приветствие, пояснение прошлого ответа). Режим задаётся конфигурацией `AGENT_PLAN_MODE = always / auto / off` | В режиме `auto` вопрос «почему DSCR просел?» по прошлому ответу не создаёт плана и не вызывает расчётов |

### Исполнение и коррекция

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| FR-5 | Исполнение по плану. Статус шага: `pending`, `in_progress`, `completed`, `skipped` (с причиной), `blocked` (ждёт ответа пользователя) | В состоянии после хода у каждого шага финальный статус; у `skipped` и `blocked` есть причина |
| FR-6 | Явное сопоставление. Расчётные инструменты принимают только ID из индекса. ID агент получает от `resolve_terms`: кандидаты с оценкой сходства. При низкой оценке агент выбирает по смыслу, переформулирует или спрашивает | Вызов расчёта с ID вне индекса отклоняется с `unknown_id`. Eval: per-param accuracy не ниже v1 |
| FR-7 | Коррекция. Ошибка инструмента возвращается модели как наблюдение с `code` и `hint`. Модель повторяет вызов с другими аргументами (до 3 раз на шаг), добавляет или пропускает шаг | Eval: ≥ 70 % ходов с ошибкой инструмента завершены корректным ответом |
| FR-8 | Завершение. Финальный ответ не принимается, пока есть шаги `pending` или `in_progress`. После N возвратов (по умолчанию 3) — ответ со списком невыполненного | Тест на скриптовой модели: ранний ответ возвращается ≤ 3 раз, затем принимается с разделом «Не выполнено» |
| FR-9 | Лимиты. Вызовов инструментов ≤ 30 за ход, вызовов модели ≤ 40, расчётов движка ≤ 10 (все числа настраиваются). Лимиты считаются на ход (`run_limit`) и не накапливаются в checkpointer. При исчерпании — частичный ответ по полученным результатам | Зацикливающаяся скриптовая модель останавливается на лимите, ответ содержит полученные цифры |
| FR-10 | Недостающие данные никогда не подставляются по умолчанию (год, цель, диапазон). Шаг → `blocked`, вопрос ровно о недостающем, план сохраняется. Ответ пользователя продолжает тот же план | Запрос без года → вопрос о годе; следующий ход «2026» доводит исходный план без повторного `resolve_terms` |
| FR-11 | Недостижимая цель — результат анализа, а не ошибка: агент сообщает ближайшую достижимую точку и при каких входах | Цель DSCR = 5 даёт шаг `completed` и вывод «недостижимо, максимум … при …» |

### Результат

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| FR-12 | Структура ответа: Вывод (1–3 предложения), Ключевые цифры (таблица), Анализ (чувствительность, запас прочности, драйверы), Где в модели (показатели и листы), Оговорки (допущения и невыполненное). Пустые разделы опускаются | Проверка структуры в eval; оценка аналитика ≥ 4 из 5 |
| FR-13 | Каждое число ответа взято из результата инструмента этого или прошлого хода либо из сообщения пользователя. Производные числа (разница, процент запаса) считает инструмент, а не LLM | `AnswerGroundingGuard` находит каждое число ответа в источниках; eval-скрипт даёт 100 % |
| FR-14 | Язык ответа — деловой русский независимо от языка вопроса. Коды ошибок, тексты исключений, ID индекса и служебные имена инструментов в ответ не попадают | Регулярная проверка ответов eval-набора на коды и traceback |
| FR-15 | Контракт ответа API сохраняется: ZIP с `txt_response.txt` и `generated/agent_output.xlsx`, состав ZIP не меняется. Трасса хода (план, статусы, сводки результатов) остаётся на сервере: журнал и Langfuse | Интеграционные тесты `tests/integration/v1_api` проходят без правок |

## 5. Архитектурные требования

Решение обязано выполнять 15 требований к качеству. Числа — предложение, фиксируются после замера базовой линии v1 (S0.4).

### Интеграция и тестируемость

| ID | Требование | Как проверяем |
| --- | --- | --- |
| AR-Q1 | Два режима подключения GigaChat (api\_key и сертификаты; жёсткий переключатель `LOCAL`, как сейчас) и скриптовая модель переключаются конфигурацией без смены кода | Один eval-набор на каждом режиме |
| AR-Q2 | Тестируемость без сети и без LibreOffice: полный цикл идёт на скриптовой модели и заглушке движка | `pytest tests/unit` в CI без ключей и без `soffice` |
| AR-Q3 | Изоляция фреймворка: связь с LangChain только в адаптере инструментов и агентном рантайме. В `tools.py` и смысловом слое новых импортов LangChain не появляется | Проверка импортов (`import-linter` или тест) |
| AR-Q4 | Воспроизводимость: версии `langchain`, `langgraph`, `deepagents`, `langchain-gigachat`, `langfuse` зафиксированы; установка идёт через внутреннее зеркало | Чистая сборка Docker-образа в закрытом контуре |
| AR-Q5 | Конфигурируемость: лимиты, пороги, режимы и список skills задаются переменными окружения через `config/agent` (pydantic-settings) | Тест конфигурации; таблица параметров в README |

### Ресурсы и конкурентность

| ID | Требование | Как проверяем |
| --- | --- | --- |
| AR-Q6 | Бюджет контекста: модель постоянно видит ≤ 8 инструментов; запрос к модели ≤ 30 тыс. токенов (`AGENT_MAX_PROMPT_TOKENS`); результат длиннее порога выносится в хранилище со ссылкой | Замер размера запроса по слоям в журнале и eval |
| AR-Q7 | Изоляция пользователей: состояние, кэши и вынесенные результаты ключуются по `user_id`; один пользователь не может прочитать чужое, даже с тем же `x-session-id` | Тест: два `user_id` с одинаковым `session_id` не видят историю друг друга |
| AR-Q8 | Конкурентность движка: не более одного расчёта на сессию одновременно, даже при параллельных tool calls; число одновременных расчётов в сервисе ограничено пулом (`AGENT_CALC_WORKERS`) | Тест с двумя параллельными расчётами в одной сессии и нагрузочный тест на N пользователей |
| AR-Q9 | Event loop не блокируется: синхронные openpyxl и LibreOffice идут в потоке или процессе | `/health` отвечает за ≤ 1 с во время расчёта |
| AR-Q10 | Производительность: одиночный запрос — p50 не хуже v1 + 20 %; составной из 3–5 шагов — p90 ≤ 180 с; таймаут хода `AGENT_TURN_TIMEOUT` (300 с) даёт частичный ответ | Замер в eval на GigaChat |

### Надёжность, наблюдаемость, безопасность

| ID | Требование | Как проверяем |
| --- | --- | --- |
| AR-Q11 | Отказоустойчивость: сетевой сбой LLM — до 3 повторов с экспоненциальной паузой; StopEvent GigaChat — без повтора, HTTP 503 (как сейчас); сбой запуска LibreOffice — 1 повтор | Тесты с инъекцией ошибок; `tests/unit/test_stop_event.py` зелёный |

## 7. Логическая архитектура

Новый код сосредоточен в двух слоях: агентном рантайме и адаптере инструментов. API меняется точечно, домен и движок переиспользуются.

&#91;embedded content: логическая архитектура · 5 слоёв и 3 внешних сервиса\]

Вызовы идут сверху вниз. К GigaChat обращаются два слоя: рантайм (цикл агента) и смысловой слой (сопоставление). Рантайм хранит историю в checkpointer, адаптер пишет результаты в store. Callbacks Langfuse подключает API.

### Компоненты

| Слой | Компонент | Ответственность | Статус |
| --- | --- | --- | --- |
| API | `api/v1/router.py` | Заголовки, `thread_id`, callbacks Langfuse, выбор агента по `AGENT_ENGINE`, сборка ZIP, маппинг исключений в HTTP | Точечная правка |
| Рантайм | `api/v2/factory.py:AgentFactory` | Собирает модель, инструменты, промпт и middleware в `create_agent`; кэширует агента на процесс | Новый |
| Рантайм | `api/v2/middleware/*` | Стек из раздела 8: контекст хода, ограничения, план, skills, лимиты, повторы, проверка ответа, выжимка | Новый |
| Рантайм | `api/v2/prompts/system.py` | Роль, правила (числа только из инструментов, не додумывать входы), границы темы, карточка модели из контекста | Новый |
| Рантайм | `api/v2/skills/` | Skills в формате `SKILL.md` + `references/`; валидируются при старте | Новый |
| Адаптер | `api/v2/tools/adapter.py` | Доменная функция → `StructuredTool`: схема аргументов, инъекция контекста, конверт, коды ошибок | Новый |
| Адаптер | `api/v2/tools/engine_gate.py` | Блокировка сессии, пул процессов `spawn`, таймаут и отмена расчёта | Новый (из `OrchestratorTools`) |
| Адаптер | `api/v2/tools/catalog.py` | Реестр инструментов и их доступность (базовые / через skill) | Новый |
| Домен | Индекс модели, смысловой слой, `tools.py` | См. раздел 2 | Без изменений |
| Движок | `lo_backend.py`, `excel_handler.py` | Пересчёт в LibreOffice | Без изменений |
| Инфраструктура | `context.py:AppContext`, `config/agent` | LLM, память, трейсинг; новые параметры агента | Дополнение |

### Правила зависимостей

1. Вызовы идут только сверху вниз: API → рантайм → адаптер → домен → движок.
2. Рантайм не импортирует `tools.py` и `src/excel_engine/` напрямую, только через адаптер.
3. Домен не знает об агенте: не читает состояние графа, план и skills.
4. Смысловой слой вызывает ту же модель GigaChat, что и агент. Вызовы идут с теми же callbacks, чтобы попасть в дерево хода Langfuse.
5. v1 (`main_graph.py`, `orchestrator_tools.py`) и v2 не импортируют друг друга; общий код — только домен и инфраструктура.

## 8. Агентный цикл

Ход начинается с плана и заканчивается, только когда каждый шаг закрыт, пропущен с причиной или ждёт ответа пользователя. Исключение — исчерпанный лимит или таймаут: тогда уходит частичный ответ.

&#91;embedded content: агентный цикл · план, исполнение, коррекция, проверка завершения\]

Ошибка возвращает ход к исполнению через коррекцию; открытый шаг — через `PlanCompletionGuard`. Из цикла есть два выхода: все шаги закрыты, либо исчерпан лимит или нужен ответ пользователя.

### Правила цикла

1. **Подготовка.** `TurnContext` берёт файл, индекс и карточку модели из реестра, `LanguageGuard` проверяет язык. Любая проваленная проверка завершает ход без вызова LLM (`jump_to="end"`).
2. **План.** В режиме плана, пока плана нет, `ForcePlanFirst` оставляет модели только `read_file` (только `/skills/`) и `write_todos` при `tool_choice = auto`. Модель может сначала прочитать подходящий skill, затем строит план. В режиме `always` ответ без вызова возвращается модели с `tool_choice = write_todos` (GigaChat не поддерживает обязательный вызов «любого из набора» — spike S0.2); `allow_any_tool_choice_fallback` не используется. Если закреплён skill, план строится по его шаблону. Если в чекпоинте есть шаги `blocked` прошлого хода, модель обновляет их статус, а не строит план заново.
3. **Сопоставление.** До первого расчёта модель вызывает `resolve_terms` сразу по всем терминам плана. Расчёт с ID вне индекса отклоняется адаптером.
4. **Исполнение.** Модель ставит шагу `in_progress`, вызывает инструменты и закрывает шаг через `write_todos`. GigaChat делает один вызов инструмента за ответ модели (spike S0.2), поэтому вызовы внутри хода всегда последовательны.
5. **Коррекция.** Ошибка приходит как наблюдение с `code` и `hint` (справочник — в разделе 10). Модель повторяет вызов с другими аргументами (до 3 раз на шаг), добавляет шаг или пропускает его с причиной. Временные сбои LLM и движка повторяют middleware, модель их не видит.
6. **Уточнение.** Недостающие данные (`missing_input`) переводят шаг в `blocked`. Независимые шаги доводятся, и ответ содержит полученные результаты плюс один вопрос о недостающем. План остаётся в чекпоинте.
7. **Завершение.** Ответ без вызовов проверяет `PlanCompletionGuard`: при открытых шагах модель получает напоминание отдельным сообщением пользователя (последним сообщением не может оставаться ответ модели: GigaChat продолжает его и выдумывает данные — spike S0.2) и возвращается к работе, не более N раз (по умолчанию 3). Затем `AnswerGroundingGuard` сверяет числа ответа с источниками: одна перегенерация, затем неподтверждённые числа убираются с оговоркой.
8. **Лимиты.** 30 вызовов инструментов, 40 вызовов модели, 10 расчётов и 300 с на ход (всё настраивается). При исчерпании — один вызов модели без инструментов для частичного ответа со списком невыполненного.
9. **Режимы плана.** `AGENT_PLAN_MODE=auto` (по умолчанию) — модель сама решает, но первый же расчётный вызов без плана отклоняется с `plan_required`; `always` — план в каждом ходе (для eval и отладки: на ходах без расчёта принудительный вызов даёт выдуманный план — spike S0.2); `off` — `ForcePlanFirst` и `PlanCompletionGuard` выключены.

### Стек middleware

Порядок значим: хуки `before_*` идут сверху вниз, `after_*` — снизу вверх, `wrap_*` вложены (первый в списке — внешний). Поэтому `PlanCompletionGuard` стоит ниже `AnswerGroundingGuard`: сначала проверяется план, потом числа.

## 9. Состояние, контекст и память

Контекст модели собирается из семи слоёв с разным сроком жизни. В каждом запросе всегда лежат только первые три. Полный индекс модели в промпт не попадает никогда — модель видит его только через `resolve_terms`.

### Слои контекста

| Слой | Содержимое | Срок жизни | Механизм |
| --- | --- | --- | --- |
| Инструкции | Роль, правила работы с инструментами, границы темы, запрет выдуманных чисел | Постоянно | `system_prompt` агента |
| Карточка модели | Имя файла, число входов и выходов, годы прогноза, ключевые метрики кредитора, единицы | Пока загружен файл | Динамический промпт из runtime context (`TurnContext`) |
| Каталог skills | Имя и описание каждого skill | Постоянно | `SkillsMiddleware` |
| Текст skill и его инструменты | Шаблон плана, правила интерпретации | Пока чтение есть в контексте | `read_file` или `AGENT_PINNED_SKILLS` |
| План | Шаги и статусы | Ход; до следующего хода, если есть `blocked` | `todos` в состоянии |
| Вызовы и результаты | Сводки; крупные результаты — ссылкой на `/results/` | Ход, до суммаризации | Сообщения + `SummarizationMiddleware` |
| Память диалога | Выжимки ходов: термины и их ID, ключевые цифры, ссылки на результаты | Сессия | Checkpointer по `thread_id` |

### Состояние агента

`CopilotAgentState` расширяет `AgentState` из `create_agent` и сохраняется checkpointer’ом.

| Поле | Тип | Срок жизни | Кто пишет |
| --- | --- | --- | --- |
| `messages` | список сообщений, reducer `add_messages` | Сессия (сжимается) | Цикл, `SummarizationMiddleware` |
| `todos` | список `{content, status, reason}` | Ход (+ `blocked`) | `write_todos`, `TurnContext` |
| `turn_id` | строка | Ход | `TurnContext` |
| `model_ref` | `{file_name, file_hash}` | Пока не загружен новый файл | `TurnContext` |
| `resolved_terms` | словарь «термин → `{id, name, score}`» | Сессия, сброс при смене файла | Адаптер `resolve_terms` (через `Command`) |
| `step_results` | список `{call_id, tool, status, code, summary, ref, numbers}` | Ход | Адаптер |
| `guard_counters` | `{plan_returns, grounding_retries, calc_calls}` | Ход | Guard-middleware |
| `turn_summaries` | последние 5 выжимок | Сессия | `TurnSummary` |

### Runtime context

`RequestContext` не сохраняется и передаётся в `agent.ainvoke(..., context=...)`: `user_id`, `session_id`, `thread_id`, `trace_id`, `client_id`, `file_path`, `deadline`. Инструменты и middleware читают его из `runtime.context`; модель его не видит.

### Правила

1. `TurnContext` в начале хода обнуляет `step_results` и `guard_counters`. `todos` обнуляется, только если в нём нет шагов `blocked`.
2. Новая загрузка файла в той же сессии (другой `file_hash`) сбрасывает `resolved_terms`, кэш расчётов и план. В контекст добавляется заметка «модель заменена», чтобы агент не ссылался на старые цифры.
3. Результат длиннее порога (ADR-7) пишется в store по ключу `("results", user_id, thread_id)` / `<turn_id>/<call_id>.json` и читается через `read_file /results/...`. В сообщения попадает только сводка.
4. Выжимку хода строит `TurnSummary` из `step_results` и `todos` без вызова LLM. В следующем ходе выжимки подаются компактным блоком в динамическом промпте.
5. Суммаризация сжимает только `messages`. План, карточка модели, `resolved_terms` и выжимки живут вне сообщений и не теряются.
6. Размер каждого слоя в токенах пишется в журнал при каждом вызове LLM (AR-Q6, AR-Q13).
7. `MemorySaver` и `InMemoryStore` живут в памяти процесса: перезапуск контейнера теряет историю (как сейчас). При нескольких репликах сервиса нужен либо sticky-роутинг по `x-user-id`, либо общий checkpointer (открытый вопрос).

## 10. Инструменты

Модель постоянно видит 8 инструментов; ещё 2 открываются после чтения skill. Все инструменты следуют одному контракту. Расчётные функции (`tools.py`, для v2 — копия в `src/excel_engine/`) не меняются по логике: адаптер переводит ID в канонические имена и вызывает их с теми же аргументами, что и v1.

### Контракт

1. **Описание.** Имя, одно-два предложения на русском «что делает и когда вызывать», схема аргументов на Pydantic. Примеры и длинные правила переносятся в skills.
2. **Вход.** Аргументы проверяются до вызова: схема, наличие ID в индексе, год в горизонте модели, `min < max`, `step > 0`, размер сетки ≤ `AGENT_MAX_GRID` (по умолчанию 400 точек). Нарушение возвращается модели как ошибка, движок не запускается.
3. **Выход.** Единый конверт: `result` (сводка на русском с единицами), `data` (компактные структурированные данные), `numbers` (список `{value, label, unit}` для проверки ответа), `notes` (оговорки), `hint` (что делать дальше), `ref` (путь к полному результату).
4. **Ошибка.** `{error, code, hint}`: `code` из справочника ниже, `hint` называет следующий шаг. Именно это позволяет модели исправить план (FR-7). Статусы v1 (`WARNING`, `INFO`, `ERROR` и текст `_humanize_error`) адаптер классифицирует в коды.
5. **Контекст.** `user_id`, путь к файлу, индекс и дедлайн берутся из `ToolRuntime`. В схеме для модели их нет.
6. **Безопасность для модели.** Исходный файл не меняется: движок открывает его ReadOnly, каждый расчёт начинается с базового состояния.
7. **Доступ к движку.** Инструмент с флагом `uses_engine` идёт через `engine_gate`: блокировка сессии → пул процессов → таймаут вызова (`AGENT_CALC_TIMEOUT`, 120 с).
8. **Точка остановки.** Перед каждым расчётом проверяются дедлайн и флаг отмены (AR-Q12).
9. **Размер.** Ответ длиннее порога уходит в `/results/`, в `ToolMessage` остаются `result`, `numbers` и `ref` (ADR-7).

### Каталог

| Инструмент | Оборачивает | Вход (видит модель) | Доступность | Движок |
| --- | --- | --- | --- | --- |
| `write_todos` | `TodoListMiddleware` | список шагов со статусами | Всегда | Нет |
| `read_file` | `FilesystemMiddleware` | путь в `/skills/` или `/results/` | Всегда | Нет |
| `resolve_terms` | `AnalyzerSubAgent` + `find_matching_cell` / `find_matching_outputs` | термины `[{text, role: input / output}]` | Всегда | Нет (вызов LLM внутри) |
| `get_values` | `get_output_info`, базовые значения входов из индекса | ID, годы | Всегда | Нет |
| `describe_model` | `describe_outputs_sheet` | — | Всегда | Нет |
| `run_scenarios` | `analyze_excel_model` | ID входов с `[min, max, step]`, ID выходов, год | Всегда | Да |
| `find_input_for_target` | `analyze_model_inputs_for_target` | ID выхода, год, цель, ID входов, допуск | Всегда | Да |
| `derive` | Новая чистая функция арифметики | ссылки на результаты, операция: разница, % изменения, запас до порога, точка пересечения порога, эластичность | Всегда | Нет |
| `set_inputs_and_recalc` | `modify_excel_input_value` | ID входов и значения, ID выходов, годы | Skill `point-what-if` (после первой волны) | Да |
| `trace_dependencies` | `build_dependency_graph` | ID выхода | Skill `sensitivity-drivers` | Нет |

`derive` — единственный новый доменный код. Он нужен, чтобы производные числа считала не LLM (FR-13). Движок пересчёта он не вызывает.

### Справочник кодов ошибок

| Код | Когда | Кто исправляет | Поведение |
| --- | --- | --- | --- |
| `invalid_args` | Аргументы не прошли проверку | Модель | Повтор с исправленными аргументами |
| `unknown_id` | ID нет в индексе | Модель | `resolve_terms`, затем повтор |
| `ambiguous_term` | Несколько кандидатов с близкой оценкой | Модель, затем пользователь | Выбор по смыслу; если нельзя — вопрос с вариантами |
| `term_not_found` | Ни один кандидат не прошёл порог | Модель, затем пользователь | Переформулировать (синоним, русское название); после 2 попыток — вопрос |
| `no_values` | Строка без формулы или значений (заголовок раздела) | Модель | Взять следующего кандидата |
| `bad_units` | Диапазон в процентах для показателя в долях или наоборот (сравнение с базовым значением) | Модель | Пересчитать единицы и повторить |

| `engine_timeout` | Расчёт превысил `AGENT_CALC_TIMEOUT` | Модель | Сузить сетку (меньше входов или крупнее шаг) |
| `plan_required` | Расчёт без плана в режиме `auto` | Модель | Вызвать `write_todos` |
| `limit_exceeded` | Исчерпан лимит расчётов или вызовов | Модель | Частичный ответ |
| `cancelled` | Дедлайн хода или разрыв соединения | Система | Ход завершается, частичный ответ |
| `internal_error` | Непредвиденное исключение | Разработчик | Шаг `skipped`, полный traceback в журнале |

Недостижимая цель — не ошибка: `find_input_for_target` возвращает успех с `data.reachable = false` и ближайшей точкой (FR-11).

## 11. Skills: сценарии сложных расчётов

Skill — это папка с `SKILL.md` в формате Agent Skills: когда применять, какие шаги плана составить, как толковать цифры и какие инструменты открыть. Skill не содержит кода расчёта и цифр конкретной модели — только методику поверх существующих инструментов (FR-18).

### Структура

- Фронтматтер: `name`, `description` (что делает и на какие слова запроса реагирует, по-русски и по-английски), `metadata.include_tools` (имена через пробел).
- Тело: шаблон плана, правила выбора аргументов (диапазоны, шаг, допуск), типичные ошибки и выход из них, формат раздела ответа. До 300 строк.
- `references/` — справочники, которые читаются по ссылке из тела: типовые пороги ковенант, трактовка DSCR / LLCR / Debt/EBITDA, глоссарий сокращений.
- Примеры запросов с ожидаемым планом лежат рядом в `evals.yaml` и не читаются моделью.

### Первая волна

| Skill | Запрос аналитика | Шаблон плана | Открываемые инструменты |
| --- | --- | --- | --- |
| `economic-answer` | Любой (закреплён всегда) | Структура ответа FR-12, стиль, формулировки выводов и оговорок | — |
| `target-seeking` | «Какой должна быть X, чтобы Y = Z?» | сопоставить → базовые значения → подбор → отклонение от базы → вывод | — |
| `scenario-analysis` | «Посчитай Y при X от a до b», «при падении на 10–30 %» | сопоставить → база (для относительных диапазонов) → сетка → изменения → вывод | — |
| `covenant-headroom` | «Хватит ли запаса по ковенантам?», «при какой цене пробьём DSCR 1,2?» | метрики и пороги → база → стресс-сетка по драйверам → точка пробоя → запас прочности | — (базовые + `references/covenants.md`) |
| `sensitivity-drivers` | «Что сильнее влияет на Y?», «почему просел Y?» | драйверы → ±N % по каждому → эластичности → рейтинг → связи в модели | `trace_dependencies` |
| `point-what-if` | «Поставь цену 500 и покажи EBITDA и DSCR» | сопоставить → база → точечный пересчёт → сравнение с базой. Не в первой волне: пока такие запросы закрывает `scenario-analysis` сеткой из одной точки | `set_inputs_and_recalc` |

### Активация

1. **Моделью.** Модель сама читает skill через `read_file`, когда запрос совпадает с описанием. Текст skill попадает в контекст до построения плана: пока плана нет, `ForcePlanFirst` оставляет доступными `read_file /skills/` и `write_todos` (§8, п. 2).
2. **Конфигурацией.** `AGENT_PINNED_SKILLS` (по умолчанию `economic-answer`) закрепляет skills для всех ходов. Это основной путь, если eval покажет, что GigaChat пропускает чтение (FR-19). Потребитель API skills не передаёт.
3. После суммаризации инструменты незакреплённого skill снова скрыты, пока модель не прочитает его заново. Промпт напоминает об этом. Вызов скрытого инструмента отклоняется с подсказкой, какой skill прочитать.

**Хранение и версии.** Skills лежат в репозитории (`src/aigw_service/api/v2/skills/`) и входят в Docker-образ. Пишет и меняет их только команда разработки; изменение проходит review, прогон eval-набора этого skill и оформляется как OpenSpec change. По данным прототипа, skill-инструменты требуют `deepagents>=0.7.22`, закрепление — `>=0.7.23`; версии проверяются в S0.1.

## 12. LLM, движок пересчёта и конкурентность

Агент работает только с GigaChat в двух режимах подключения. Расчёты одной сессии всегда последовательны, расчёты разных сессий делят пул процессов.

### Провайдеры

| Подключение | Реализация | Что проверить в spike |
| --- | --- | --- |
| GigaChat по api\_key | `langchain-gigachat`, `GIGACHAT_CREDENTIALS` при `LOCAL=true` | Обновление токена; принудительный вызов функции (`tool_choice`); несколько tool calls в одном ответе; `functions_state_id`; смена набора инструментов посреди диалога; ответ, когда последнее сообщение не от человека (известная проблема v1) |
| GigaChat по сертификатам (внутренний контур) | `langchain-gigachat` с клиентским сертификатом и ключом (mTLS), CA-bundle, `base_url` контура | Цепочка сертификатов, ротация; те же проверки вызова инструментов |
| Скриптовая модель | `ScriptedChatModel` за `BaseChatModel` с поддержкой `bind_tools` | Детерминированный полный цикл для тестов и демо |

Модель собирается один раз на процесс в `AgentFactory` из настроек `config/gigachat`. Смысловой слой использует ту же модель. StopEvent распознаёт middleware `StopEventGuard` в `wrap_model_call` (§8). Spike S0.2: обёртка `context.py:_wrap_llm_with_stop_event` на пути `create_agent` тоже срабатывает, но в v1 не подключена (bugfix `fix-v1-stop-event-503`); в v2 подмена методов модели не нужна. Подтверждено spike: принудительный вызов по имени, `functions_state_id`, смена набора инструментов посреди хода, обновление токена (в том числе после 401), ответ после `ToolMessage` с инструментами и без.

### Движок и потоки

1. **Пул.** Расчёт идёт в `ProcessPoolExecutor` с контекстом `spawn` (как сейчас в `OrchestratorTools`), размер — `AGENT_CALC_WORKERS`. Сейчас воркер один на весь сервис, то есть расчёты всех пользователей идут в очереди. Дефолт v2 выбирается по замеру памяти одного `soffice` в S0.4.
2. **Блокировка сессии.** Инструменты `uses_engine` берут `asyncio.Lock` по `thread_id`. Внутри хода вызовы и так последовательны (один вызов инструмента за ответ модели — spike S0.2); блокировка защищает движок, если в сессии всё же окажутся два расчёта одновременно.
3. **Блокировка хода.** Второй запрос в тот же `thread_id`, пока идёт ход, сразу получает HTTP 409 «предыдущий запрос ещё обрабатывается, направьте следующий вопрос позже». Иначе два хода перемешают план и историю в чекпоинте. Блокировка хода отдельна от блокировки сессии из п. 2, иначе параллельные вызовы `ToolNode` зависнут.
4. **Event loop.** Построение индекса и чтения через openpyxl / pandas идут в `asyncio.to_thread`, расчёты — в пуле, вызовы LLM — асинхронные (AR-Q9).
5. **Таймаут расчёта.** При `AGENT_CALC_TIMEOUT` адаптер возвращает `engine_timeout`. Зависший воркер нельзя остановить через `Future.cancel`, поэтому `engine_gate` пересоздаёт пул, а воркер в `finally` завершает свой `soffice` (AR-Q12).
6. **Кэши.** LRU-кэш `tools.py` живёт внутри воркера (как сейчас). `CalcCache` — уровень сессии в store и не зависит от того, какой воркер считал. Индекс и карточка модели — в реестре моделей в store по хэшу файла.
7. **Процессы uvicorn.** Один процесс приложения: `MemorySaver` и блокировки живут в памяти. Несколько процессов или реплик требуют общего checkpointer и распределённой блокировки — вне рамок, но интерфейсы не должны этому мешать.

## 13. API, наблюдаемость, отказоустойчивость и безопасность

Внешний контракт не ломается: все изменения добавочные. Клиент, который не знает о v2, работает как раньше.

### Контракт API

| Аспект | Сейчас (v1) | v2 |
| --- | --- | --- |
| `POST /api/v1/upload` | Сохраняет `/tmp/user_file_{user_id}.{ext}`, пишет имя в store | Контракт без изменений. При AGENT\_ENGINE=v2 дополнительно строит индекс и карточку модели и пишет их в реестр по `file_hash`; новый файл даёт новую запись |
| Заголовки | 5 заголовков, 422 при несовпадении | Без изменений; `thread_id = "{user_id}:{session_id}"` |
| Тело `/invoke-agent` | `CopilotAgentRequest` | Без изменений |
| Ответ | ZIP: `txt_response.txt`, `generated/agent_output.xlsx` | Без изменений |
| Нет загруженного файла | `ValueError` → ошибка 500 | 200, ответ «загрузите модель» (FR-1) |
| GigaChat недоступен (StopEvent) | 503 | 503, без изменений |
| Идёт предыдущий ход сессии | Не обрабатывается | 409 сразу, с просьбой направить вопрос позже |
| Таймаут хода | Нет | 200, частичный ответ с оговоркой |

### Наблюдаемость

- **Журнал.** Loguru, как сейчас. На каждый вызов LLM — JSON из `build_diagnostic_data` с временем, токенами, инструментами в ответе и размером слоёв контекста. Исключения пишутся только через `logger.opt(exception=True).error("...: {}", str(e))` — f-строки с `{}` в тексте ошибки роняют loguru.
- **Совместимость с eval-скриптами.** `scripts/run_tool_queries.py` разбирает строки `TOOL ARGS` по именам и аргументам v1. Адаптер пишет эти строки после перевода ID в канонические имена, с v1-именами функций (`analyze_excel_model`, `analyze_model_inputs_for_target`) и v1-формой аргументов. Так сравнение v1 и v2 идёт одним и тем же скриптом.
- **Трассировка.** Self-hosted Langfuse во внутреннем контуре через текущий callback-handler (`router.py:get_cb_handler`). Дерево хода: узлы middleware, вызовы LLM, инструменты, вложенные вызовы смыслового слоя. `langfuse_session_id = thread_id`, `langfuse_user_id = user_id`, тег `agent_engine=v2`.
- **Сводка хода на сервере.** `TurnSummary` пишется в журнал сервера и в Langfuse: план, статусы, сопоставленные термины, числа и коды ошибок без текстов исключений.
- **Метрики хода.** Длительность, число вызовов LLM и расчётов, исход (полный / частичный / уточнение / отказ) — через существующий механизм метрик, без правки `metric_router.py`.

### Отказоустойчивость

| Сбой | Поведение |
| --- | --- |
| Сетевая ошибка или 5xx GigaChat | 3 повтора с паузой. Затем частичный ответ, если есть результаты, иначе 503 |
| StopEvent GigaChat | Ход прерывается сразу, 503 |
| Сбой LibreOffice | 1 повтор, затем шаг `skipped`, остальные шаги продолжаются |
| Зависший расчёт | `engine_timeout`, пул пересоздаётся, `soffice` завершается |
| Таймаут хода или разрыв соединения | `Cancellation` завершает ход после текущего вызова; чекпоинт остаётся согласованным |
| Невалидный ответ модели (битые аргументы вызова) | `invalid_args` возвращается модели, лимит повторов — как для ошибок инструмента |
| Перезапуск контейнера | История сессий теряется (как сейчас); файлы в `app_tmp` сохраняются |

### Безопасность

- У агента нет инструментов записи файлов и `execute`. Backend `read_file` ограничен `/skills/` и `/results/`; пространство `/results/` берётся из `user_id` в runtime context, а не из пути, поэтому чужие результаты недоступны.
- В LLM уходят подписи строк и числа из результатов инструментов, не файл целиком.
- Содержимое ячеек — данные, а не инструкции: подписи передаются в полях данных, системный промпт прямо запрещает исполнять текст из результатов.
- Трейсинг только в контуре; при `LANGSMITH_TRACING=true` сервис не стартует (AR-Q14).
- Ключи и сертификаты — в `.env` и `certs/`, как сейчас; в журнал и Langfuse не пишутся.

## 14. Тестирование и оценка качества

Качество агента измеряется eval-набором на живом GigaChat, а не только unit-тестами. v2 становится агентом по умолчанию, когда не уступает v1 по всем метрикам и достигает целей G1–G3.

### Уровни

| Уровень | Что проверяем | На чём |
| --- | --- | --- |
| Домен | Существующие расчёты и матчер не изменились | Текущие тесты (`test_russian_stemmer`, `test_tools_performance`) |
| Адаптер | Схемы, перевод ID в имена, конверт, классификация ошибок v1 в коды, вынос результатов, `engine_gate` (блокировка, таймаут, пересоздание пула) | Unit-тесты с заглушкой движка |
| `derive` | Арифметика, интерполяция точки пробоя, единицы | Property-based тесты |
| Middleware | `TurnContext`, `LanguageGuard`, `ForcePlanFirst`, `PlanCompletionGuard`, `AnswerGroundingGuard`, `CalcCache`, `Cancellation`, `TurnSummary` | `ScriptedChatModel` |
| Агент целиком | Сценарии U1–U9 (ниже) сквозным ходом | `ScriptedChatModel` + заглушка движка |
| Коннектор | Формат запросов GigaChat с функциями в обоих режимах подключения | Эмуляция API (`httpx.MockTransport`) |
| API | ZIP, 409, 503, 422, изоляция пользователей, переключатель v1 / v2 | `httpx.AsyncClient(app=...)`, `tests/integration/v1_api` |
| Интеграция с LibreOffice | Полный ход на настоящем движке, отсутствие сирот `soffice` | Docker, тестовая книга в репозитории |
| Eval | Качество решения реальных запросов | Живой GigaChat, оба режима подключения |

| --- | --- | --- | --- |

### Метрики eval

- **Доведение плана:** доля ходов, в которых все шаги `completed` или закрыты с причиной (FR-8, G1).
- **Покрытие планом:** доля действий из эталонного разбора запроса, попавших в план (FR-3).
- **Восстановление после ошибки:** доля ходов с ошибкой инструмента, завершённых корректным ответом (FR-7, G2).
- **Точность цифр:** каждое число ответа найдено в результатах вызовов; проверяется скриптом (FR-13, G3).
- **Per-param accuracy:** доля правильно сопоставленных параметров, текущими `run_tool_queries.py` и `analyze_results.py` (FR-6, G5).
- **Ожидаемые инструменты и skills:** нужные инструменты вызваны, нужный skill прочитан, лишний — нет.
- **Точность уточнений:** вопрос задаётся только при реальной нехватке данных и только о ней (FR-10).
- **Стоимость:** число шагов, вызовов LLM, токены, время хода, число пересчётов (AR-Q10).
- **Оценка аналитика:** качество вывода по шкале 1–5 на выборке из 20 ответов (FR-12, G3).

**Наборы.** Регрессия одиночных запросов — `tests/data/Methanex_tool_test_queries.xlsx`. Новый набор составных запросов `tests/data/eval_v2.yaml`: 30 запросов на 2–3 моделях, для каждого — эталонные шаги, ожидаемые ID терминов, ожидаемые числа с допуском и ожидаемый skill. Тестовая книга для CI хранится заранее пересчитанной, чтобы unit-тесты не зависели от LibreOffice.

## 16. Риски и открытые вопросы

Главный риск — совместимость GigaChat с механикой `create_agent` (принудительный вызов инструмента, смена набора инструментов). Его снимает spike S0.2 до основной разработки.

| Риск | Последствие | Что делаем |
| --- | --- | --- |
| `langchain-gigachat` не поддерживает принудительный `tool_choice`, несколько вызовов в ответе или смену инструментов | `ForcePlanFirst` и skill-инструменты не работают | Снят spike S0.2 (api_key; в контуре — проверить по сертификатам): вызов по имени и смена инструментов работают; «любой из набора» и несколько вызовов не поддерживаются — учтено в §8 п. 2 и п. 4 |
| Кандидаты с оценками нельзя получить без правки `AnalyzerSubAgent` | ADR-4 под угрозой | Spike S0.3. Запасной вариант: кандидаты напрямую из `find_matching_*`, `AnalyzerSubAgent` — только для выбора лучшего |
| Слабая модель не читает skill | Нужные инструменты остаются скрытыми, методика не применяется | `AGENT_PINNED_SKILLS`; метрика «нужный skill прочитан» в eval |
| Больше вызовов LLM на ход | Рост латентности и стоимости | Лимиты, режим `auto`, кэши индекса и расчётов; замер в S0.4 и S5.1 |
| Встроенные промпты middleware на английском | Смешение языков, лишние токены | Переопределить `system_prompt` и описания инструментов (S2.1) |
| Быстрые изменения API `deepagents` 0.x | Поломка при обновлении | Жёсткие версии (S0.1); middleware подключаются только через `AgentFactory` |
| Один воркер расчёта на весь сервис | Пользователи ждут друг друга; составной запрос занимает пул надолго | `AGENT_CALC_WORKERS` по замеру памяти; лимит расчётов на ход |
| `AnswerGroundingGuard` ложно срабатывает на округлениях, единицах и годах | Лишние перегенерации, вырезанные верные числа | Нормализация чисел, допуск на округление, исключение годов и номеров; доля срабатываний — метрика в eval |
| `MemorySaver` и store растут без очистки | Рост памяти процесса | Вынос больших результатов из сообщений; переключение на внешнюю БД конфигурацией (открытый вопрос) |

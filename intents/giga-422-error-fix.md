# Intent
Исправить ошибку 422 GigaChat every assistant function call must have a result in history, возникающую при продолжении сессии после сбоев в выполнении инструментов оркестратором.

## Why Now
Ошибка блокирует работу с агентом в текущей сессии: после любой ошибки в tool_executor (424) пользователь теряет возможность продолжить диалог — требуется перезапуск сессии. Это критично для UX и
надёжности сервиса.

## Тип Intent
System Evolution — исправление ошибки в логике мультиагентного графа, приводящей к разрыву истории сообщений и несовместимости с GigaChat API.

## Ожидаемое улучшение
После выполнения Intent:
    - tool_executor всегда создаёт ToolMessage для каждого вызванного инструмента — даже при внутренних ошибках
    - При достижении лимита итераций оркестратора unexecuted tool_calls закрываются заглушками
    - История сообщений в checkpointer всегда удовлетворяет требованию GigaChat (каждый tool_call_id имеет соответствующий ToolMessage)
    - Пользователь может продолжать диалог в той же сессии независимо от внутренних ошибок инструментов

## Критерии успеха
    1. Функциональный: При эмуляции exception в _execute_single_call (или _run_ift, _run_ema) — следующий invoke сессии не возвращает 422
    2. Интеграционный: При достижении MAX_ORCHESTRATOR_ITERATIONS — unexecuted tool_calls закрываются `ToolMessage`-заглушками через узел `force_execute_remaining`
    3. Регрессионный: Штатные сценарии orchestrator → tool_executor → orchestrator → synthesizer продолжают работать без изменений

## Ограничения
    - Не менять API GigaChat — решение работает в рамках текущего контракта
    - Не изменять интерфейс /invoke-agent и структуру ответа ZIP
    - Не удалять checkpointer и историю сессий — они нужны для UX
    - Не использовать try/catch на 422 как решение — исправляется только корневая причина
    - Сохранить MAX_ORCHESTRATOR_ITERATIONS как механизм защиты от бесконечного цикла

## Риски
    - Неожиданные побочные эффекты: добавление узла force_execute_remaining в граф может повлиять на существующие тесты
    - Производительность: force_execute_remaining добавляет ~5-10мс к каждому invoke, где срабатывает cap (редкий сценарий)
    - Неполное покрытие: если есть другие пути попадания unexecuted tool_calls в историю — они могут остаться неохваченными (нужно проверить все пути маршрутизации)

## Why

Эпик E6 добавляет потоковый `/invoke-agent/stream`: фронт показывает план и ход работы, пока агент считает. Spike S6.1 подтвердил источник событий (ADR-14: `agent.astream(stream_mode=["updates", "custom"], version="v2")`), составил таблицу «узел LangGraph → событие прогресса» и показал, что ход нужно запускать отдельной задачей (H3). В коде этого пока нет: `AgentV2` умеет только `answer()` через `ainvoke`, схемы событий нет, подписей вызовов и текстов ошибок для пользователя нет. Endpoint S6.3 и сводки S6.4 строятся поверх этого слоя, поэтому он нужен первым и проверяется без HTTP — на скриптовой модели.

## What Changes

- Новый пакет `api/v2/stream/`:
  - **Схема событий `v = 1`** (§13 «Каталог событий»): pydantic-модели `turn.started`, `phase`, `plan`, `tool.started`, `tool.finished`, `summary`, `answer`, `error` с общими полями `v`, `seq`, `ts`, `trace_id`. Схема описывает весь каталог. Поля, которые наполняет S6.4 (сводка шага в `tool.finished`, событие `summary`, фазы от `ProgressReporter`), в S6.2 объявлены, но не заполняются.
  - **`StreamTranslator`** — чистый переводчик частей `astream` в события по таблице S6.1. Начало вызова — из обновления `model` с `tool_calls`, конец — из обновления `tools` с `ToolMessage`, план — из `todos`. Текстовый ответ модели считается кандидатом и даёт фазу `checking`. Кандидат, отклонённый guard-middleware (`jump_to`), отбрасывается. Служебные узлы middleware событий не дают. Части `custom` (фаза и исход `retry`) переводятся по объявленному формату; писать их начнёт `ProgressReporter` в S6.4.
  - **Подписи вызовов** на русском по таблице «инструмент → шаблон» (§13 «Подписи и сводки») из аргументов вызова и канонических имён индекса, без ID.
  - **Таблица «код → текст для пользователя»** и исход `retry` / `failed` по коду конверта ошибки. Это не `ERROR_TEXT`: тот адресован модели.
  - **Исход хода** для `answer`: `full` / `partial` / `clarify` / `refusal`. Он выводится из состояния хода (`guard_counters`, `todos`, ответ `TurnContext` / `LanguageGuard`).
  - **Гигиена FR-24**: текст от модели и пользователя в плане и подписях чистится от ID индекса, имён инструментов, путей `/results/` и кодов. Функция проверки события на запрещённое содержимое используется в тестах и пригодится S6.5.
- **`AgentV2.stream()`** рядом с `answer()`. Блокировка хода берётся при вызове, до первого события, поэтому `TurnBusyError` (409 в S6.3) возникает до открытия потока. Дедлайн и `RequestContext` те же, что у `answer()`. Ход идёт в отдельной `asyncio`-задаче, события передаются через неограниченную очередь, так что медленный потребитель не задерживает ход. Поток заканчивается ровно одним терминальным событием: `answer` с тем же текстом, что вернул бы `answer()`, или `error` (`unavailable` при `StopEventError`, `failed` при прочем исключении). Если потребитель уходит, ставится `RequestContext.cancel`, а блокировка снимается с концом хода, а не потока (AR-Q17).
- Документация: §13 спецификации (формат частей `custom`, таблица «код → текст», правило исхода хода); `openspec/traceability.md` — строки FR-22, FR-24.

**Вне рамок:** HTTP endpoint, кадры SSE, heartbeat, правка `log_requests`, 409 / 422 / 503 на уровне HTTP, упрощённый поток v1, OpenAPI (S6.3); `ProgressReporter`, фазы `planning` / `executing` / `answering`, исход `retry` при повторе движка, сводки шагов и событие `summary` (S6.4); строка `STREAM`, тег Langfuse, параметры `AGENT_STREAM_*`, метрика потоков (S6.5); ответ по токенам (снят решением ADR-15); чистка текста финального ответа (он обязан совпадать с `txt_response.txt`); изменения в стеке middleware и в `answer()` сверх общего кода подготовки хода.

## Capabilities

### New Capabilities

- `agent-stream`: потоковая доставка хода агента v2. Требования-владельцы S6.2: FR-22 «Прогресс хода в потоке» и FR-24 «Гигиена потока» (ADDED). Также ADR-14 «Ход потока в отдельной задаче, события из обновлений узлов» (ADDED здесь: это контракт `AgentV2.stream()`, на который опираются S6.3 и S6.4). FR-21, FR-25, FR-26 и AR-Q17 принадлежат S6.3, их HTTP-часть остаётся там.

## Impact

- Новые файлы:
  - `src/aigw_service/api/v2/stream/__init__.py`, `events.py` (схема), `labels.py` (подписи, «код → текст», очистка), `translator.py` (`StreamTranslator`), `turn.py` (`TurnStream`: задача, очередь, терминальное событие), `hygiene.py` (проверка события);
  - `tests/unit/v2/test_stream_translator.py`, `tests/unit/v2/test_stream_turn.py`.
- Изменяемые файлы:
  - `src/aigw_service/api/v2/service.py` — метод `stream()` и общая с `answer()` подготовка хода;
  - `src/aigw_service/api/v2/turn/lock.py` — `acquire()` — захват блокировки с функцией освобождения, которую вызывает задача хода; `hold()` переписывается через него без изменения поведения (design D9);
  - `docs/Copilot cashflow analyst v2 project spec.md` — §13 «Потоковый режим»;
  - `openspec/traceability.md` — FR-22, FR-24, ADR-14.
- Ни `router.py`, ни HTTP-контракт, ни стек middleware не меняются: без S6.3 метод `stream()` никто не вызывает. `answer()` ведёт себя как раньше.
- Зависимостей не добавляется: `astream(..., version="v2")` уже есть в `langgraph` 1.2.16 (S6.1, P2).

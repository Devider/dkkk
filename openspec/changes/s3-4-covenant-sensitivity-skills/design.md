# Design

## Context

Мотивация описана в proposal.md, требования — в `specs/agent-skills/spec.md` и `specs/agent-tools/spec.md`. Опорные разделы спецификации: §10 «Каталог», §11 «Первая волна» и «Активация» п. 3, ADR-2 (skill-инструменты из `deepagents`), ADR-5 (расчёт по ID), ADR-9 (производные числа считает `derive`).

Что уже есть:
- `ToolSpec.availability` — `BASE` или имя skill. `ToolCatalog.skill_tools()` передаётся в `SkillsMiddleware(tools=...)` (S3.1). Сейчас этот набор пуст.
- `SkillsMiddleware` (deepagents 0.7.29) показывает инструмент после `read_file` skill и, пока его текст в контексте, прикрепляет его к вызову в `wrap_tool_call`. Если модель вызывает инструмент, который ещё не показан, `request.tool` остаётся `None`, и `ToolNode` отвечает общей ошибкой неизвестного инструмента. Скрытие после сжатия истории проверено в S2.7 (`test_skill_tools_hidden_after_compression`).
- `ForcePlanFirst` отклоняет вызов без плана конвертом `plan_required` прямо из `wrap_tool_call`. Это образец для отклонения скрытого инструмента.
- `derive`: операции `headroom` (с `direction` `min` / `max`), `crossing` (с ближайшей точкой, если порог не пересечён) и `elasticity` (по двум точкам). Операнды берутся только из источников: `step_results`, выжимки прошлых ходов и сообщения пользователя. Порог из запроса пользователя уже считается источником (`numbers_in_text`), «1,2» разбирается как 1.2. Текст skill источником не считается (S4.1, `lc_source`).
- `run_scenarios` кладёт в `numbers` значения сетки входа и выходов. Поэтому для `crossing` и `elasticity` точки берутся из источников.
- Лимиты хода по умолчанию: 10 расчётов, 30 вызовов инструментов, 40 вызовов LLM (FR-9).
- `build_dependency_graph` v1 ищет выход по описанию через Jaccard, пропускает диапазоны (`A1:B2`) и рисует PNG через graphviz в `excel_scripts/`. Функции обхода (`parse_cell_ref`, `get_direct_dependencies`, `build_dependency_graph_from_cell`) лежат только в v1 `tools.py`, в `src/excel_engine/` их нет.
- В Methanex лист `Outputs` содержит DSCR, ICR, Net Debt/EBITDA и их варианты (LTM, корр.), но пороги ковенант в книге не заданы. Значения выходов разложены по колонкам годов (заголовок — год). Строки входов и выходов нумеруются в ID функциями `create_input_mapping` / `create_output_mapping` (поле `row`), как в `index_builder.py`.

## Goals / Non-Goals

**Goals:**
- Первый настоящий skill-инструмент и проверка всей цепочки: скрыт → `skill_required` → прочитан → выполнен → после сжатия снова скрыт.
- Два skill, которые доводят U2 и U8 до проверяемого ответа без новых доменных расчётов: только существующие инструменты и `derive`.
- Детерминированные сквозные проверки на скриптовой модели и eval-скрипт, готовый к прогону в контуре.

**Non-Goals:**
- Изменение правил источников FR-13: порог из skill источником не становится (решение пользователя).
- Изменение `ModelIndex` и реестра моделей: строки и колонки для обхода `trace_dependencies` находит сам.
- Визуализация графа, правка v1.

## Decisions

### D1. Отклонение скрытого инструмента: `SkillToolGate` и код `skill_required`

Новый middleware `api/v2/middleware/skill_gate.py`. Он получает отображение «имя инструмента → skill» из `ToolCatalog` (по `availability != BASE`). В `wrap_tool_call` / `awrap_tool_call`: если `request.tool is None` и имя есть в отображении, middleware возвращает `ToolMessage(status="error")` с конвертом `failure(ErrorCode.SKILL_REQUIRED, hint="Прочитай /skills/<skill>/SKILL.md через read_file и повтори вызов.")`. Иначе он вызывает `handler`.

Место в стеке `AgentFactory.middleware()` — сразу после `skills_middleware`, то есть внутри него. `SkillsMiddleware` к этому моменту уже прикрепил показанный инструмент, поэтому `request.tool is None` означает «не показан». Gate стоит снаружи `ForcePlanFirst`: если плана нет и модель вызывает скрытый инструмент, она получает `skill_required`. Подсказка о skill полезнее: без неё вызов не пройдёт и с планом. Имя, которого нет в каталоге (`write_file`), gate пропускает, и сообщение остаётся прежним (сценарий AR-Q14).

Код `skill_required` добавляется в `ErrorCode`, в подсказки по умолчанию и в справочник FR-7. Он не входит в `TRANSIENT_CODES`. Это отклонение от §10 «Справочник кодов ошибок»: ни один существующий код не говорит «прочитай skill». `invalid_args` заставил бы модель менять аргументы, а `plan_required` — вызывать `write_todos`. Альтернатива «оставить ошибку неизвестного инструмента» отвергнута: §11 п. 3 требует подсказку, какой skill прочитать.

Gate не пишет `step_results`, как и `plan_required`: инструмент не выполнялся. `TurnLimits` считает вызов как обычный вызов инструмента.

### D2. Обход формул: `src/excel_engine/dependencies.py`

Чистая функция без LangChain (AR-Q3):
`trace(workbook, start: tuple[sheet, cell], stop_sheets: set[str], max_cells: int) -> Trace`.

- Основа — логика v1 `get_direct_dependencies` / `parse_cell_ref`: `openpyxl.formula.Tokenizer`, операнды `RANGE`. Это новая функция в модуле копии движка, тела функций v1 не меняются (неизменяемые компоненты §2). Отличия от v1:
  - диапазоны `A1:B10` и `'Лист'!A1:B10` раскрываются в ячейки;
  - обход идёт в ширину (BFS) и для каждой ячейки запоминает наименьшую глубину;
  - ячейки листов из `stop_sheets` (лист `Inputs`) не раскрываются дальше: это листья;
  - обход останавливается, когда пройдено `max_cells` ячеек, и выставляет `truncated`;
  - ссылки на другие книги (`[1]Лист!A1`), именованные диапазоны и ошибки `#REF!` пропускаются и считаются в `skipped`.
- Результат: `{(sheet, row): min_depth}` для ячеек листов `Inputs` и `Outputs`, плюс `visited`, `truncated` и `skipped`.
- Предел `MAX_TRACE_CELLS = 20000` — константа модуля, без новой настройки окружения. Целые столбцы (`A:A`) и диапазон больше предела не раскрываются: они считаются в `skipped`, и результат получает оговорку.

Альтернатива — обернуть `build_dependency_graph` v1, как сказано в §10. Она отвергнута по трём причинам: v1 ищет выход по тексту (а v2 работает по ID, ADR-5), пропускает диапазоны (а `SUM` по строкам в cashflow-моделях — основной способ связи) и пишет PNG на диск. Это отклонение от §10 «Оборачивает».

### D3. Инструмент `trace_dependencies` (`api/v2/tools/dependencies.py`)

- Схема: `output_id: str | None` и `year: int | None` (необязательны в схеме: отсутствие — это `missing_input`, как у других инструментов, §10 п. 2). Предпроверки до открытия книги:
  - ID есть в индексе — иначе `unknown_id`;
  - у выхода есть значения — иначе `no_values`;
  - год в `output_years` — иначе `invalid_args` с перечнем доступных лет.
- Адрес старта: строка выхода и колонка года. Их даёт `cell_map(path)`: проход по листам `Inputs` / `Outputs` (`data_only=True`) теми же `create_input_mapping` / `create_output_mapping`, что в `index_builder.py`. Получаются `IN<i> → row`, `OUT<i> → row` и `year → column` по заголовку. Нумерация совпадает с индексом по построению. Тест сверяет её с `build_model_index` на синтетической книге.
- Книга с формулами (`openpyxl.load_workbook(data_only=False)`) и `cell_map` кэшируются в процессе через `functools.lru_cache(maxsize=2)` по `(path, mtime_ns, size)`. На Methanex загрузка книги занимает секунды, а в «почему просел» и в рейтинге драйверов `trace_dependencies` может вызываться повторно. Кэш только читается. openpyxl-книга без записи безопасна для параллельного чтения из потоков: обход только читает ячейки.
- Результат (конверт ADR-5):
  - `result` — «EBITDA, 2026 зависит от N входов модели; ближайшие: …» (до 10 названий по глубине);
  - `data.inputs` — `[{id, name, depth}]` по глубине, затем по ID;
  - `data.outputs` — промежуточные выходы `[{id, name, depth}]` без стартового;
  - `data.visited`, `data.truncated`;
  - `numbers` — только счётчики («Входов в связях», «Пройдено ячеек»);
  - `notes` — обрезка и пропуски;
  - `hint` — «Возьми базовые значения входов через get_values; для рейтинга — сетку ±10 % по каждому и derive elasticity».
  - Длинный список уходит в `/results/` штатным адаптером (ADR-7).
- `ToolSpec(availability="sensitivity-drivers", uses_engine=False)`: `engine_gate`, лимит расчётов и `CalcCache` его не касаются. Регистрация — в `default_catalog()`.
- PNG и graphviz не используются: потребитель API картинку не получает, а модель её не читает.

*Найдено при реализации (замер на Methanex, задача 3.3):* название входа может повторяться в листе `Inputs`: «Цена на природный газ на хабе Henry Hub» стоит в трёх строках. Функции разметки v1 хранят по названию одну строку — последнюю, и туда же смотрит индекс и пересчёт. А формулы EBITDA ссылаются на строку 249. Если сопоставлять только строки индекса, главный драйвер себестоимости метанола выпадает из связей. Решение: `cell_map` даёт ID названия каждой строке с этим названием (`normalize_text`, как в разметке), а `input_rows` хранит строку индекса. Если вход достигнут только через другую строку, результат перечисляет его и добавляет оговорку: сетка по этому входу может не изменить показатель. Сам индекс и разметка v1 не меняются (неизменяемые компоненты §2).

### D4. `covenant-headroom/SKILL.md` и `references/covenants.md`

Описание (`description`): «Запас по ковенантам и точка пробоя: «хватит ли запаса по DSCR», «при какой цене пробьём DSCR 1,2», «Net Debt/EBITDA не выше 3», «covenant headroom», «breach point», «stress test». Без `include_tools`.

Тело (ориентир ~120 строк, лимит 300):
- **Когда применять / когда нет.** Есть показатель-ковенант и вопрос о запасе или пробое. «Как изменится DSCR при цене 300–500» без порога и запаса — это `scenario-analysis`. «Какая цена даёт DSCR ровно 1,2» без сетки — это `target-seeking`. Если в запросе есть сетка и порог, работает этот skill (U2).
- **Шаблон плана** (образец формулировок, в угловых скобках заглушки):
  1. Метрики и пороги — `resolve_terms` для показателей и драйвера; порог и направление записываются из запроса.
  2. База — `get_values` метрик и драйвера за год; `derive headroom` базы до порога.
  3. Стресс-сетка — `run_scenarios` по драйверу в абсолютных единицах (относительный диапазон переводится по правилам `scenario-analysis`; шаг не назван — 5 точек).
  4. Точка пробоя — `derive crossing` по точкам сетки (x — драйвер, y — метрика) и порогу.
  5. Запас прочности — `derive pct_change` от базы драйвера к точке пробоя.
  6. Вывод.
- **Порог только от пользователя.** Порога нет в сообщениях пользователя — шаг «Метрики и пороги» получает `blocked` с причиной, расчётов нет, ответ — один вопрос: «Какой порог по <показатель> заложен в кредитной документации?». Значение не подсказывается. Если пороги названы только для части метрик, считаются эти метрики, а вопрос задаётся по остальным в «Оговорках», без блокировки всего плана.
- **Направление.** Берётся из `references/covenants.md`: DSCR, ICR, LLCR — `min` («не ниже»), Debt/EBITDA и Net Debt/EBITDA — `max` («не выше»). Если пользователь назвал направление явно («не ниже», «не более»), берётся его вариант.
- **Нет драйвера или диапазона стресса** («хватит ли запаса по DSCR 2026, порог 1,2»): считается только запас базы (шаги 1, 2, 6). Стресс-шаги в план не входят, а «Оговорки» предлагают назвать драйвер и диапазон. FR-10 запрещает выдумывать диапазон, а запас базы — уже ответ на вопрос.
- **Нет года** — `blocked` и вопрос о годе, как в S3.3.
- **Порог не пересечён в сетке** — заметка `derive` о ближайшей точке. Вывод: «в диапазоне <a–b> порог не пробивается; минимум <показатель> = … при …». Сетка без просьбы не расширяется.
- **Разделы ответа.** «Ключевые цифры»: база метрики, порог, запас (абсолютный и % от порога), точка пробоя, запас прочности драйвера. «Оговорки»: порог взят из запроса, направление, шаг сетки, линейная интерполяция точки пробоя.

`references/covenants.md` (~60 строк) — таблица «показатель → формула словами → направление → как читать запас» для DSCR, DSCR с долгом, LLCR, ICR, Debt/EBITDA, Net Debt/EBITDA, а также глоссарий сокращений (LTM, корр.). Числовых порогов нет. Это отклонение от §11 «Структура» («типовые пороги ковенант» в `references/`), причина — решение пользователя: порог только из запроса. Так ответ не опирается на число, которого нет ни в источниках, ни в договоре клиента.

### D5. `sensitivity-drivers/SKILL.md`

Описание: «Что сильнее всего влияет на показатель и почему он изменился: «что сильнее влияет на EBITDA», «ключевые драйверы», «почему просел DSCR», «от чего зависит», «sensitivity», «drivers», «tornado», «why did X drop». `metadata.include_tools: trace_dependencies`.

Тело (ориентир ~130 строк):
- **Ветка А — рейтинг влияния.** Шаблон «драйверы → ±N % по каждому → эластичности → рейтинг → связи в модели»:
  1. Сопоставить выход (и драйверы, если пользователь их назвал).
  2. Драйверы. Если пользователь их не назвал — `trace_dependencies` выхода за год и до 5 входов с наименьшей глубиной и ненулевой базой (`get_values`). Если назвал — берутся названные, не больше 5.
  3. Сетка по каждому драйверу — отдельный `run_scenarios` с одним входом: `min = база × 0,9`, `max = база × 1,1`, `step = max − min` (две точки). *Найдено при реализации:* движок строит сетку `np.arange(min, max + 1e-10, step)`, и шаг, округлённый вверх хотя бы на ulp больше `max − min`, даёт одну точку. Поэтому skill задаёт шаг как `max − min` и велит округлять его вниз. Входы в одну сетку не объединяются, иначе получится декартово произведение.
  4. Эластичность — `derive elasticity` по двум точкам каждого драйвера.
  5. Рейтинг по модулю эластичности — порядок в тексте, без новых чисел.
  6. Связи в модели — промежуточные выходы из `trace_dependencies` в разделе «Где в модели». Это отклонение от порядка §11: если драйверы не названы, связи нужны до расчёта, чтобы их выбрать. Иначе этот шаг идёт последним, как в §11.
- **Сдвиг ±N %.** Если пользователь назвал сдвиг, берётся его. Иначе ±10 %, и «Оговорки» говорят «сдвиг ±10 % от базы выбран по умолчанию». Это не выдумывание диапазона по FR-10: вопрос пользователя — «что влияет сильнее», и сдвиг задаёт только способ измерения. Эластичность от небольшого симметричного сдвига почти не зависит от N. Обоснование то же, что для шага сетки в S3.3 D2. Альтернатива «спросить N» отвергнута: на вопрос «что сильнее влияет» аналитик ждёт ответа, а не встречного вопроса.
- **Сдвиг в «Оговорках».** *Найдено при реализации:* числа «±10 %» нет ни в одном источнике, поэтому `AnswerGroundingGuard` (FR-13) снял бы его из ответа. Skill велит один раз получить сдвиг через `derive pct_change` (база первого драйвера → верхняя точка его сетки) и писать в ответе результат. Так же в S3.3 точки сетки вместо числа шага.
- **Лимит расчётов.** 5 драйверов дают 5 расчётов из 10 на ход. Если `limit_exceeded`, ответ строится по посчитанным драйверам, а остальные перечисляются в «Оговорках».
- **Ветка Б — «почему просел Y»** (U8). Если в этом диалоге уже есть выжимка с нужными цифрами, ответ строится из неё без инструментов (FR-16, U8 «без пересчёта»). Иначе:
  1. Сопоставить выход.
  2. `get_values` выхода за оба года. Если год сравнения не назван — предыдущий год горизонта; это сравнение двух соседних фактических значений, а не подстановка параметра расчёта. «Оговорки» говорят, с каким годом сравнили.
  3. `trace_dependencies` за более поздний год.
  4. `get_values` до 10 ближайших входов за оба года.
  5. `derive pct_change` для входов, которые изменились.
  6. Вывод: входы с наибольшим относительным изменением. «Оговорки»: это совпадение по времени, а не разложение вклада.

  Пересчёт движком в ветке Б не нужен.
- **Нет года** (ветка А) — `blocked` и вопрос о годе.
- **Разделы ответа.** «Ключевые цифры»: эластичности в порядке рейтинга (ветка А) или изменения выхода и входов (ветка Б). «Где в модели»: путь «вход → промежуточные выходы → показатель» по названиям, без ID (FR-14).

### D6. `evals.yaml`

Формат S3.3 D3. В `expect.tools` может быть `trace_dependencies`.
- `covenant-headroom`, 5 запросов:
  - CH1 — U2 целиком;
  - CH2 — только запас базы с порогом;
  - CH3 — без порога (ожидается вопрос);
  - CH4 — Net Debt/EBITDA с `max`;
  - CH5 — английский запрос.
- `sensitivity-drivers`, 5 запросов:
  - SD1 — «что сильнее влияет на EBITDA 2026» без драйверов;
  - SD2 — с названными драйверами и ±20 %;
  - SD3 — «почему просел DSCR 2027 к 2026»;
  - SD4 — без года (ожидается вопрос);
  - SD5 — английский запрос.

Unit-тест проверяет формат и то, что `skill` и `tools` существуют в поставке и каталоге.

### D7. Тесты на скриптовой модели и eval-скрипт

`tests/unit/v2/test_covenant_sensitivity_skills.py` использует каркас `test_scenario_skills.py`: настоящий `AgentFactory`, `default_catalog()`, skills из поставки, `InlineGate`, подменённый домен v1, заглушка `resolve_terms`. Для `trace_dependencies` используется синтетическая книга в `tmp_path` (openpyxl с формулами: `Inputs`, `Calc`, `Outputs`), согласованная с индексом заглушки. Сценарии:
- **Скрытый инструмент:** `trace_dependencies` до чтения — `skill_required` с путём; затем `read_file` skill и тот же вызов — успех. После сжатия истории (приём из `test_summarization`) снова `skill_required`. `write_file` — прежняя ошибка неизвестного инструмента.
- **U2** (`covenant-headroom`): `get_values` → `derive headroom` (порог 1.2 из запроса) → `run_scenarios` → `derive crossing` → `derive pct_change`. Все шаги `completed`, ответ не изменён `AnswerGroundingGuard`, нарушений структуры и гигиены нет.
- **Без порога:** шаг `blocked`, `derive` не вызывался, ответ — вопрос, в тексте нет числа порога.
- **Рейтинг** (ветка А) и **почему просел** (ветка Б); в ветке Б расчётных инструментов нет.
- **Состав поставки:** пять skills валидны; до чтения модель видит 8 инструментов, после чтения `sensitivity-drivers` — 9.

`tests/unit/v2/test_trace_dependencies.py` проверяет функцию обхода и инструмент: глубина, диапазоны, цикл, обрезка, межлистовые ссылки, сверка `cell_map` с `build_model_index`, предпроверки, отсутствие обращения к движку и неизменность файла (mtime и хэш).

`scripts/eval/scenario_skills.py`: `SKILLS` расширяется до четырёх сценарных skills, добавляется флаг `--skills` для выбора. Метрики те же (S3.3 D5). Живой прогон на GigaChat — задача «в контуре». Результаты дописываются в раздел «Результаты», иначе сценарий «Свои eval-запросы проходят» на живой модели остаётся открытым до S5.1 / S5.3, как в S3.3.

## Risks / Trade-offs

- [GigaChat вызывает `trace_dependencies`, не прочитав skill] → `skill_required` с путём даёт один дополнительный вызов `read_file`; в eval это метрика «прочитан skill».
- [Обход формул на большой модели медленный или упирается в предел] → BFS с пределом 20 000 ячеек, кэш разобранной книги, оговорка об обрезке; вызов идёт в рабочем потоке (AR-Q9). Замер времени на Methanex — задача в tasks.
- [openpyxl-книга с формулами занимает сотни МБ на больших моделях] → кэш на 2 книги; при росте памяти — `maxsize=1` или без кэша (константа).
- [Глубина формул — плохой прокси важности драйвера] → драйверы ветки А ранжируются по эластичности из пересчёта, а глубина используется только для отбора кандидатов.
- [Ветка Б выдаёт совпадение по времени за причину] → обязательная оговорка «не разложение вклада»; формулировки выводов задаёт `economic-answer`.
- [Без порога агент только спрашивает и кажется менее полезным] → это решение пользователя; вопрос один и конкретный, а запас считается на следующем ходе без повторного сопоставления (FR-16).
- [Сдвиг ±10 % по умолчанию воспринимается как подстановка] → одно правило, всегда в «Оговорках»; пользователь меняет его следующим ходом.
- [Межкнижные ссылки и именованные диапазоны дают неполный список входов] → счётчик `skipped` и оговорка; именованные диапазоны можно раскрывать позже без изменения спеки.

## Migration Plan

Добавляются папки двух skills, модуль `excel_engine/dependencies.py`, инструмент, gate и код ошибки. Откат: удалить папки skills и регистрацию `trace_dependencies`, убрать `SkillToolGate` из фабрики. Код `skill_required` можно оставить: без skill-инструментов он не возникает.

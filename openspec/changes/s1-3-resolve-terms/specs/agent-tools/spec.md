# Spec Delta

## ADDED Requirements

### Requirement: FR-6 Явное сопоставление терминов

Инструмент `resolve_terms` SHALL принимать термины пользователя с ролью (вход или выход модели) и возвращать по каждому термину кандидатов из индекса модели `{id, name, score}` и уровень уверенности `high` или `low`. Первым кандидатом SHALL идти выбор смыслового слоя. Уверенность SHALL быть `high`, только если выбор смыслового слоя совпадает с одним из лучших по лексическому сходству имён индекса. Смысловой слой при этом не меняется.

#### Scenario: Термин сопоставлен уверенно
- **WHEN** модель вызывает `resolve_terms` с термином, для которого выбор смыслового слоя входит в тройку лучших по лексическому сходству
- **THEN** результат термина содержит этого кандидата первым и `confidence: high`

#### Scenario: Термин сопоставлен неуверенно
- **WHEN** выбор смыслового слоя не входит в тройку лучших по лексическому сходству (например, английский термин при русских именах)
- **THEN** результат термина содержит выбор смыслового слоя первым, ещё до двух кандидатов и `confidence: low`

#### Scenario: Термин не найден
- **WHEN** для термина нет ни выбора смыслового слоя, ни кандидата с ненулевым сходством
- **THEN** результат этого термина — `term_not_found` с подсказкой переформулировать, остальные термины вызова сопоставляются как обычно

#### Scenario: Роль учитывается
- **WHEN** термин передан с ролью `output`
- **THEN** все его кандидаты — выходы модели, а не входы

### Requirement: FR-6 Устойчивость сопоставления

Сбой одного термина MUST NOT ронять сопоставление остальных. Временная недоступность модели из-за ограничения частоты запросов SHALL повторяться с паузой.

#### Scenario: Смысловой слой падает на одном термине
- **WHEN** смысловой слой падает при обработке списка терминов
- **THEN** инструмент повторяет сопоставление по одному термину, и термины, которые разрешаются по отдельности, получают кандидатов

#### Scenario: Ограничение частоты запросов
- **WHEN** GigaChat отвечает на вызов смыслового слоя ограничением частоты (HTTP 429)
- **THEN** вызов повторяется с паузой, и модель получает результат, а не ошибку, если повтор успешен

### Requirement: FR-6 Сопоставленные термины в состоянии

Результат `resolve_terms` SHALL сохраняться в состоянии агента как соответствие «термин → `{id, name, confidence}`» по первому кандидату, чтобы последующие шаги и ходы могли использовать его без повторного сопоставления.

#### Scenario: Термины попадают в состояние
- **WHEN** `resolve_terms` сопоставил термины
- **THEN** в состоянии агента есть `resolved_terms` с этими терминами, их ID, каноническими именами и уверенностью

#### Scenario: Повторное сопоставление дополняет состояние
- **WHEN** в ходе вызывается `resolve_terms` для новых терминов
- **THEN** новые термины добавляются к уже сопоставленным, прежние не теряются

### Requirement: FR-6 Точность не ниже v1

Доля правильно сопоставленных параметров через `resolve_terms` SHALL быть не ниже, чем у v1 на том же наборе запросов эталона.

#### Scenario: Сравнение с v1 на эталоне
- **WHEN** скрипт оценки прогоняет выборку эталона Methanex через `resolve_terms` и через анализатор v1 на исходных запросах
- **THEN** per-param accuracy `resolve_terms` по первому кандидату не ниже v1 на запросах, где оба отработали

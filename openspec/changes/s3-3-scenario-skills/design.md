# Design

## Context

Мотивация — proposal.md, требования — `specs/agent-skills/spec.md`. §11 «Структура», «Первая волна», «Активация» п. 1; ADR-9 (ответ пишет агент), ADR-5 (расчёт по ID); FR-3, FR-10, FR-11, FR-13.

Что уже есть и на что skills опираются (кода не добавляем):
- Каталог skills в промпте и чтение `read_file /skills/...` — S3.1; до плана `ForcePlanFirst` пропускает только `write_todos` и чтение `/skills/` (FR-3), поэтому skill читается раньше плана.
- Базовые инструменты: `resolve_terms`, `get_values`, `describe_model`, `run_scenarios`, `find_input_for_target`, `derive`. Оба skill обходятся ими — `metadata.include_tools` нет.
- Предпроверки (S1.4): нет года / цели / диапазона → `missing_input`; год вне горизонта, пустой выход, неверный диапазон, сетка больше `AGENT_MAX_GRID` → `invalid_args` / `no_values`; доля вместо процента → `bad_units`. Недостижимая цель — успех с `data.reachable = false` и заметкой (FR-11).
- `run_scenarios` кладёт в `numbers` каждое значение сетки входа (S1.7 D5), `find_input_for_target` — базовые значения входов. Значит абсолютный диапазон из относительного и базы попадают в источники FR-13, если модель передала их в сетку.
- `derive`: `difference`, `pct_change`, `headroom`, `crossing`, `elasticity`; операнды — только числа из источников.
- `economic-answer` закреплён и задаёт разделы FR-12; skills сценариев говорят только, что положить в разделы.
- Прогон S3.2 на GigaChat: год выдумывается (Q5), подбор вызывается без аргументов (Q3), выбор между «Метанол» и «Этилен» при однозначном термине (Q2, Q4).
- Живой GigaChat доступен только во внутреннем контуре (эпик 5).

## Goals / Non-Goals

**Goals:**
- Два skill, которые закрывают наблюдения S3.2 правилами и образцами, а не кодом.
- Детерминированная проверка U1 и U3 сквозным ходом на скриптовой модели с настоящими middleware и каталогом.
- Готовый к запуску в контуре eval-скрипт, который берёт запросы из `evals.yaml` skills.

**Non-Goals:**
- Изменения логики `api/v2/` вне `skills/`. Единственное отклонение — текст описания поля `step` (D6).
- Закрепление этих skills (S3.5) и метрики eval-набора (S5.1).

## Decisions

### D1. `target-seeking/SKILL.md`

Фронтматтер: `description` — «Подбор значения входа модели, при котором показатель достигает цели: «какой должна быть X, чтобы Y = Z», «при какой цене EBITDA будет…», «what X gives Y = Z», «break-even», «target».

Тело (≤ 300 строк, ориентир ~120):
- **Когда применять / когда нет:** цель — конкретное значение выхода в конкретном году. «Посчитай Y при X от a до b» — не этот skill (`scenario-analysis`); «при какой цене DSCR пробьёт 1,2 по сетке» — сетка + `derive crossing` (`scenario-analysis`; до S3.4).
- **Шаблон плана** (4–5 шагов, формулировки — образец, не текст для копирования):
  1. Сопоставить показатели (`resolve_terms`: выход — role `output`, подбираемые входы — role `input`; одним вызовом).
  2. Базовые значения: `get_values` выхода и входов за год цели.
  3. Подбор: `find_input_for_target` с `output_id`, `year`, `target`, `input_ids` — все четыре из запроса и сопоставления; `tolerance` не трогать, если пользователь не назвал допуск.
  4. Отклонение от базы: `derive pct_change` (и `difference` при необходимости) — база входа → найденное значение.
  5. Вывод (ответ по `economic-answer`).
- **Правила аргументов:** цель — число без единиц, в единицах выхода; проценты для долевых выходов — как доля, если `get_values` показывает «доля». Нет года или цели → шаг подбора `blocked` с причиной, ответ — один вопрос о недостающем (FR-10); никогда не брать «текущий год» или «последний год модели». Термин сопоставлен `high` — не спрашивать выбор показателя (наблюдение S3.2).
- **Ошибки по кодам:** `missing_input` — не повторять вызов без аргументов, передать их из запроса или спросить; `invalid_args` (год вне горизонта) — назвать доступные годы и спросить; `low`-уверенность — сверить кандидатов, иначе вопрос названиями.
- **Недостижимая цель** (`reachable = false`): не ошибка; вывод «Недостижимо: максимум … при …» из ближайшего сценария (FR-11), без повтора подбора с другими параметрами без просьбы пользователя.
- **Разделы ответа:** «Ключевые цифры» — база входа, найденное значение, достигнутое значение выхода, отклонение от базы (из `derive`); «Оговорки» — допуск подбора, если цель достигнута не точно.

### D2. `scenario-analysis/SKILL.md`

Фронтматтер: `description` — «Пересчёт показателей по сетке значений входа: «посчитай Y при X от a до b», «при падении/росте X на 10–30 %», «±20 %», «а если X = 500», «what if», «scenario», «sensitivity range».

Тело:
- **Шаблон плана:**
  1. Сопоставить показатели.
  2. Базовое значение входа — `get_values` за год расчёта. **Обязателен** для относительного диапазона («на 10–30 %», «±20 %»); для абсолютного — когда нужно сравнение с базой.
  3. Сетка — `run_scenarios` в абсолютных единицах.
  4. Изменения к базе — `derive pct_change` / `difference` для крайних точек (если спрашивают «как изменится»).
  5. Вывод.
- **Относительный диапазон → абсолютный** (U3): min = база × (1 − a), max = база × (1 + b), шаг = база × шаг %; «падение на 10–30 %» — min = база × 0,7, max = база × 0,9. Это аргументы инструмента, не числа ответа: ответ берёт границы сетки из результата `run_scenarios` (значения сетки есть в `numbers`). - **Шаг не назван** — не спрашивать: сетка из 5 точек, шаг = (конец − начало) / 4 («от 300 до 500» → 50; «±20 %» → 10 % от базы; «падение на 10–30 %» → 5 % от базы); в «Оговорках» — что шаг выбран по умолчанию и точки сетки. Само число шага в ответ не пишется: его нет ни в одном результате, и `AnswerGroundingGuard` (FR-13) возвращает такой ответ на перегенерацию — найдено при реализации (прогон U3 с «шаг 40» в оговорках); точки сетки есть в `numbers` `run_scenarios`. Одно правило вместо «3–5 точек», чтобы сетка была предсказуемой и проверяемой в eval. Это не «придумывание диапазона»: FR-10 запрещает выдумывать год, цель и диапазон — они меняют, что считается; шаг меняет только плотность сетки. Альтернатива «переспрашивать шаг» отвергнута: U2 («при падении на 10–30 %», шага нет) ждёт доведённого плана в одном ходе, а v1 шаг не спрашивает (без шага движок берёт 0,5 — `excel_engine/calculations.py`), так что вопрос ухудшил бы v2 против v1. В наборе Methanex шаг указан во всех 276 запросах с диапазоном — на паритет правило не влияет.
- **Одна точка** («а если X = 500»): `min = max = 500`, `step = 1` — сетка из одной точки, сравнение с базой (вместо `point-what-if`, §11).
- **Единицы:** база с единицей «доля» → диапазон в долях (5 % = 0,05); `bad_units` — пересчитать и повторить.
- **Лимит сетки:** несколько входов перемножают точки; `invalid_args` о лимите — увеличить шаг или сузить, о выбранном — в «Оговорках».
- **Нет года** → шаг сетки `blocked`, один вопрос о годе (наблюдение S3.2 Q5). Год один на все выходы; несколько лет — отдельные вызовы.
- **Разделы ответа:** «Ключевые цифры» — строка на сценарий («Метанол = 320»), база отдельной строкой; «Анализ» — направление и крутизна (если считали — эластичность из `derive`); «Оговорки» — «±20 % от базы 400 → 320–480; шаг не назван — сетка из 5 точек: 320, 360, 400, 440, 480» — числа только из результатов.

### D6. Описание поля `step` (отклонение от «логика вне `skills/` не меняется»)

Сейчас `InputRange.step` описан как «Шаг сетки; не придумывай, если пользователь не задал» — модель видит это в схеме `run_scenarios` при каждом вызове, и это противоречит D2. Противоречивые указания схемы и skill GigaChat выполняет непредсказуемо, а схема видна и без чтения skill.

Новое описание: «Шаг сетки; если пользователь не назвал — (конец − начало) / 4, а в оговорках перечисли точки сетки». Меняется только текст поля; предпроверка `missing_input` для `step = None` остаётся (срабатывает, если модель шаг вообще не передала, — подсказка та же). Описания `min` / `max` («не придумывай») не трогаются. Причина отклонения: правило шага — свойство инструмента, а не одного skill; оставлять запрет в схеме значит ломать D2.

### D3. `evals.yaml`

Один формат на оба skill (будущие skills берут его же):

```yaml
- id: TS1
  query: "Какой должна быть цена метанола, чтобы EBITDA в 2026 году была 1000?"
  expect:
    skill: target-seeking
    plan_includes: [базов, подбор]          # подстроки шагов плана, регистр не важен
    tools: [resolve_terms, get_values, find_input_for_target]
    answer: analytic                        # analytic | question
    caveat_includes: []                     # подстроки раздела «Оговорки»
```

По 4–6 запросов на skill: точный подбор, недостижимая цель (DSCR = 5, U6), без года (ожидается вопрос), английский запрос; для сетки — абсолютный диапазон, «±20 %» (U3), «падение на 10–30 %», без шага (ожидается расчёт и шаг в оговорках), одна точка, без года. `validate_skills` файл не проверяет; формат проверяет unit-тест.

### D4. Сквозные тесты на скриптовой модели

`tests/unit/v2/test_scenario_skills.py`, как `TestFactoryTurn` (`test_runtime.py`): настоящий `AgentFactory`, `default_catalog()`, каталог skills из поставки, `InlineGate`, домен v1 подменён (`analyze_excel_model` / `analyze_model_inputs_for_target` возвращают фиксированный результат), `resolve_terms` — заглушка анализатора. Режим плана `auto`.
- **U3:** `read_file /skills/scenario-analysis/SKILL.md` → `write_todos` (шаг «Базовое значение…» до шага сетки) → `resolve_terms` → `get_values IN1 2027` (база 400) → `run_scenarios` 320–480, шаг 40 → `write_todos` все `completed` → ответ с разделами и «Оговорками» «±20 % от базы 400 → 320–480; …сетка из 5 точек: 320, 360, 400, 440, 480». Проверки: `read_file` вернул текст skill (не `plan_required`); `get_values` раньше `run_scenarios`; ответ не изменён `AnswerGroundingGuard` (нет «н/д»); `structure_issues` и `hygiene_issues` пусты.
- **U1:** то же для `target-seeking` с `find_input_for_target` и `derive pct_change`.
- **Без шага:** «от 300 до 500» → `run_scenarios` 300–500 шаг 50 в том же ходе, «Оговорки» с точками 300…500, вопроса нет; описание поля `step` в схеме инструмента, которую видит модель, — новое (D6).
- **Без года:** модель ставит шаг `blocked` и задаёт вопрос; расчётный инструмент не вызывался, ответ — не аналитический и без нарушений гигиены.
- **Состав поставки:** три skill валидны; в системном промпте первого вызова есть пути обоих новых skill; набор инструментов модели после чтения skill не меняется.
- **Тексты skills:** шаблон плана содержит шаги в порядке §11; есть правила FR-10, U3 и FR-11; `evals.yaml` разбирается и ссылается на существующие skill и инструменты.

Скриптовая модель проверяет обвязку (skill читается до плана, числа U3 проходят FR-13, гигиена), а не то, что GigaChat следует skill, — это D5.

### D5. Eval-скрипт `scripts/eval/scenario_skills.py`

Каркас `answer_structure.py` (S3.2): запросы — из `evals.yaml` обоих skill; на запрос — своя сессия. Метрики на запрос: прочитан ли ожидаемый skill (и не прочитан ли лишний сценарный), `plan_includes`, вызваны ли `tools`, тип ответа, `caveat_includes`, `structure_issues` / `hygiene_issues`, вызовы модели и инструментов, время. JSON в `scripts/eval/results/scenario_skills_<режим>_<дата>.json`. `--scripted` — скриптовая модель по сценарию на запрос, без сети и движка.

Живой прогон и паритет с v1 (per-param accuracy и время на `Methanex_tool_test_queries.xlsx` через `run_tool_queries.py` / `analyze_results.py`) — задача «в контуре»; результаты дописываются в раздел «Результаты» до архивации, если прогон сделан, иначе сценарий «Паритет с v1» остаётся открытым до S5.3 (как FR-3 «покрытие ≥ 90 %» до S5.1).

## Risks / Trade-offs

- [GigaChat не читает skill, хотя запрос совпадает с описанием] → описания со словами-триггерами на двух языках; метрика «прочитан skill» в D5; закрепление по конфигурации — S3.5 (FR-19).
- [Модель копирует шаблон плана и примеры дословно, как в S3.2] → шаблоны с заглушками в угловых скобках и пометкой «образец»; числа примеров условные и в ответ не переносятся (FR-13 их отловит).
- [Модель считает абсолютный диапазон неточно] → допустимо: это аргументы; ответ берёт границы из `numbers` сетки, а не из своей арифметики.
- [Шаг сетки по умолчанию выглядит как подстановка] → разрешён только шаг, по одному правилу (5 точек), и точки сетки всегда в «Оговорках»; пользователь меняет его следующим ходом.
- [5 точек на каждый из нескольких входов быстро упираются в `AGENT_MAX_GRID`] → правило лимита из D2: увеличить шаг и сказать об этом в «Оговорках».
- [Скриптовые тесты зелёные, а на GigaChat skill не работает] → критерий «паритет с v1» не закрывается без живого прогона; отмечено в traceability.

## Migration Plan

Только файлы skills, тесты и текст описания поля `step`. Откат — удалить папки `target-seeking/` и `scenario-analysis/` и вернуть прежнее описание `step`.

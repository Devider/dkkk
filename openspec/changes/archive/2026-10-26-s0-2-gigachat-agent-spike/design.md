# Design

## Context

Мотивация — proposal.md. Проверяемые решения: ADR-3 (`ForcePlanFirst` через `tool_choice`), ADR-9 (финальный ответ пишет агент), ADR-10 (A/B preview-модели в middleware), AR-Q11 (повторы, StopEvent → 503). Список проверок коннектора — §12 «Провайдеры».

Текущее состояние (по коду, 2026-10-26):
- `config/gigachat`: `LOCAL=True` + `GIGACHAT_CREDENTIALS` → режим api_key; `LOCAL=True` + `GIGACHAT_TLS_CERT_FILEPATH` / `GIGACHAT_KEY_FILEPATH` → сертификаты (mTLS, `ssl_context`). `base_params` готовы для `GigaChat(**params)`. Локально настроен api_key, модель `GigaChat-3-Pro`.
- `langchain-gigachat` 0.5.1, `bind_tools`: `tool_choice` — `"auto"`, `"none"`, имя инструмента или `{"name": ...}`; `"any"` → `ValueError` (или `auto` при `allow_any_tool_choice_fallback=True`). Сериализация `AIMessage` с несколькими `tool_calls` → `ValueError`.
- `core/llm_executor.Agent(GigaChat)` переопределяет `invoke` / `ainvoke` / `bind_tools` для фоновой A/B-проверки preview-модели.
- `context.py:_wrap_llm_with_stop_event` определена, но не вызывается; `router.py` ловит `StopEventError` и отдаёт 503, но исключение никто не выбрасывает.
- `main_graph.py:249`: обход v1 — GigaChat даёт вырожденный ответ, если последнее сообщение промпта не от человека (в synthesizer без инструментов).

## Goals / Non-Goals

**Goals:**
- По каждому пункту §12 — подтверждённый ответ на живом GigaChat в режиме api_key и (в контуре) по сертификатам.
- Решения по ADR-9, ADR-10, месту проверки StopEvent и механике `ForcePlanFirst`, с которыми можно начинать E1–E2 без переделок.

**Non-Goals:**
- Промышленный код middleware: стенд одноразовый, прототипы middleware в нём — только для проверки механики.
- Оценка качества сопоставления имён и расчётов (S0.3, S0.4).

## Decisions

### D1. Стенд вне приложения

`scripts/spikes/s0_2_gigachat/`: `run.py` (CLI: `--checks C1,C3 --out <файл>`), `checks.py` (по функции на проверку), `fixtures.py` (фиктивные инструменты и длинный контекст). Модель — `GigaChat(**APP_CONFIG.gigachat.base_params, model=...)`, поэтому режим подключения переключается тем же `LOCAL` и `.env`, что и у сервиса (AR-Q1). `aigw_service.context` не импортируется: его импорт поднимает `APP_CTX` со всеми клиентами. Инструменты — чистые функции без LibreOffice.

*Альтернатива:* pytest-набор — отвергнута: проверки ходят в живой GigaChat и не должны попадать в `pytest tests` и CI (AR-Q2).

### D2. Проверки

| # | Что проверяем (§12 / ADR) | Как | Критерий «работает» |
| --- | --- | --- | --- |
| C1 | Базовый цикл `create_agent` | Запрос на 1 инструмент → ответ | Инструмент вызван, финальный ответ — текст |
| C2 | Обновление токена (api_key) | Подменить кэшированный токен клиента на просроченный, повторить вызов | Вызов успешен без ошибки 401 наружу |
| C3 | Принудительный вызов (ADR-3) | Middleware `wrap_model_call` ставит `tool_choice="write_todos"` на первом вызове; отдельно — `tool_choice="any"` | Первый tool call — `write_todos`; для `any` зафиксировано поведение |
| C4 | Несколько вызовов в ответе | Запрос на два независимых инструмента | Число `tool_calls` в каждом `AIMessage`; цикл доходит до ответа |
| C5 | `functions_state_id` | Цикл из ≥ 3 вызовов | Поле приходит и передаётся обратно; ошибок API нет |
| C6 | Смена инструментов посреди хода | Middleware открывает инструмент B только после вызова A (механика skill) | B вызывается; ошибок из-за изменившегося набора нет |
| C7 | Последнее сообщение не от человека | (а) вызов после `ToolMessage` в цикле; (б) вызов без инструментов после `ToolMessage` (частичный ответ, §8 п. 8); (в) после `AIMessage` | Ответ осмысленный, не вырожденный |
| C8 | StopEvent (AR-Q11) | Подменить вызов API клиента на `ForbiddenError` с маркером | Где видно исключение: в `wrap_model_call`, в `ModelRetryMiddleware` (повторяет ли), в обёртке подкласса |
| C9 | A/B preview (ADR-10) | `Agent` из `llm_executor` в `create_agent`; счётчик вызовов переопределённых методов против числа вызовов модели; прототип `PreviewModelCheck` в `wrap_model_call` | Обходит ли `create_agent` переопределения; работает ли прототип в фоне без влияния на ответ |
| C10 | Длинный контекст, финальный ответ (ADR-9) | 3 составных запроса, ~20 тыс. токенов результатов инструментов в истории, системный промпт со структурой FR-12; для сравнения — тот же ответ отдельным вызовом с чистым контекстом (synthesizer) | Структура FR-12, все числа из результатов, деловой русский; ответы сохраняются для оценки разработчиком |

Режим сертификатов: C1, C3–C8 тем же `run.py` в контуре (C2 относится к api_key, C10 — по желанию).

### D3. Критерии решений

- **ADR-3 / `ForcePlanFirst`:** если C3 подтверждает только имя инструмента — остаётся запасной путь §8 п. 2 (до плана видны `read_file` и `write_todos`; ответ без вызова возвращается с `tool_choice="write_todos"`).
- **ADR-9:** агент пишет ответ сам, если в C10 ≥ 2 из 3 ответов проходят структуру и проверку чисел и разработчик не видит потери стиля; иначе — проход synthesizer в `after_agent`.
- **ADR-10:** если C9 подтверждает обход переопределений — A/B переносится в middleware (как в ADR); иначе ADR пересматривается.
- **StopEvent:** если в C8 обёртка подкласса не на пути — проверка маркера идёт в `wrap_model_call` отдельного middleware, внешнего относительно `ModelRetryMiddleware`, а `ModelRetryMiddleware` не повторяет `StopEventError`.
- **Несколько вызовов:** если C4 подтверждает один вызов за ход — §12 п. 2 упрощается (очередь расчётов сессии по-прежнему нужна для разных ходов и инструментов), параллельные `tool_calls` не рассматриваются.

## Risks / Trade-offs

- [Недетерминизм модели: один прогон не доказывает поведение] → C3–C7 по 3 прогона, в отчёте доля успехов.
- [Квота и стоимость вызовов GigaChat] → весь набор ≈ 60–80 вызовов; C10 самый дорогой, запускается отдельно.
- [Режим сертификатов недоступен локально] → задача «в контуре»; решения по ADR, не зависящие от режима, принимаются по api_key, расхождения в контуре фиксируются дополнением отчёта.
- [Подмена внутренностей клиента в C2 / C8 ломается при обновлении `gigachat`] → это стенд под зафиксированные версии S0.1.

## Migration Plan

Не применяется: в приложение ничего не попадает. Стенд остаётся в `scripts/spikes/` до S5.4.

### C8 подробно (StopEvent, без сети)

| Вариант | Вызовов API | Что выходит из `agent.ainvoke` |
| --- | --- | --- |
| `ModelRetryMiddleware()` по умолчанию | 3 | Исключения нет; последнее сообщение — «Model call failed after 3 attempts with ForbiddenError: 403 …» |
| `ModelRetryMiddleware(on_failure="error")` | 3 | `ForbiddenError` |
| Обёртка v1 `_wrap_llm_with_stop_event` на модели | 1 | `StopEventError` (обёртка на пути: `RunnableBinding` вызывает `ainvoke` модели) |
| Прототип `StopEventGuard` снаружи `ModelRetryMiddleware(retry_on=не StopEvent, on_failure="error")` | 1 | `StopEventError` |

В v1 `_wrap_llm_with_stop_event` нигде не вызывается, поэтому StopEvent сейчас уходит наружу как `ForbiddenError`, а не HTTP 503.

### Решения

- **ADR-3 / `ForcePlanFirst`.** Обязательного вызова «любого из набора» в GigaChat нет на уровне API (HTTP 400), SDK и коннектора. Принудительный вызов по имени надёжен (3/3), но на запросе без расчёта модель выдумывает аргументы. Решение:
  1. Запасной путь §8 п. 2 становится основным: до плана модели видны только `read_file /skills/` и `write_todos`, `tool_choice="auto"`.
  2. `tool_choice="write_todos"` ставится только при повторе, если модель ответила без вызова, и только когда ход требует расчёта: в режиме `always` — всегда, в `auto` — никогда (там расчёт без плана отклоняется с `plan_required`).
  3. `allow_any_tool_choice_fallback` не включать: он молча снимает гарантию вызова.
  4. Режим по умолчанию — `AGENT_PLAN_MODE=auto` вместо `always`: в `always` приветствие или вопрос по прошлому ответу получат принудительный план с выдуманным содержанием, а FR-4 и так требует ходов без плана. `always` остаётся для eval и отладки. Пересматривает решённый вопрос §16 «Режим плана по умолчанию».
- **Несколько вызовов.** Один tool call за ход — свойство API и коннектора. Параллельных вызовов внутри хода нет, §12 п. 2 упрощается: блокировка сессии нужна только против параллельных ходов (её закрывает блокировка хода, п. 3) и как защита в `engine_gate`.
- **Возврат модели к работе (`PlanCompletionGuard`, `AnswerGroundingGuard`).** По C7 (в): `jump_to="model"` обязан добавить сообщение-напоминание (`HumanMessage`), последним сообщением не может оставаться ответ модели.
- **StopEvent (AR-Q11).** Отдельный middleware `StopEventGuard` в `wrap_model_call`, внешний относительно `ModelRetryMiddleware`; у `ModelRetryMiddleware` — `retry_on`, исключающий StopEvent, и `on_failure="error"`. С `on_failure="continue"` (по умолчанию) текст исключения попадает в ответ пользователю — нарушение FR-14. Обёртка `object.__setattr__` в v2 не нужна.
- **ADR-10.** Довод ADR неверен: подкласс не обходится. Решение (A/B в middleware) сохраняется по другим причинам: с подклассом каждый вызов модели проходит и `bind_tools`, и `ainvoke`, и при включённой проверке ставит в очередь две проверки; middleware видит весь `ModelRequest` (системный промпт, инструменты), включается конфигом и не требует подкласса `GigaChat`. Preview-модель доступна только во внутреннем контуре — проверить там.
- **ADR-9.** Решено (разработчик, 2026-10-26): агент пишет ответ сам. Отдельный synthesizer не лучше (0/3 против 1/3), структуру FR-12 дают оба, а вызов LLM на ход дороже. Ни один вариант не держит FR-13 без внешних мер: инструмент `derive` (S1.7) и `AnswerGroundingGuard` (S4.1) обязательны, а в системном промпте нужен явный запрет считать самостоятельно. Оценка разработчика: содержательно слабы оба варианта (неверные выводы, самостоятельный счёт, выдуманная таблица), преимущества у synthesizer нет.

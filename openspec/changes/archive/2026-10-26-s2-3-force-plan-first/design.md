# Design

## Context

Мотивация — proposal.md, требования — `specs/agent-planning/spec.md`. ADR-3, §8 правила 2 и 9, стек №11, §10 `plan_required`, spike S0.2 (C3, решение по ADR-3).

Состояние:
- `TodoListMiddleware` (S2.1) даёт инструмент `write_todos` и поле состояния `todos`; промпт и описание — русские.
- `TurnContext` (S2.2) в начале хода очищает `todos`, если в нём нет шагов `blocked`; поэтому «план есть» в начале хода значит «остался план с `blocked`».
- `ModelRequest.override(tools=..., tool_choice=...)` меняет набор инструментов и `tool_choice` одного вызова; `ModelResponse.result` — список сообщений ответа.
- `wrap_tool_call` получает `ToolCallRequest` (`tool_call`, `state`, `runtime`) и может вернуть `ToolMessage`, не вызывая инструмент.
- GigaChat (S0.2): `tool_choice` по имени соблюдается 3/3; «любой из набора» — HTTP 400; на запросе без расчёта принудительный вызов даёт выдуманные аргументы; один вызов инструмента за ответ; последним сообщением не может быть ответ модели.
- Код `plan_required` с текстом и подсказкой уже есть в `ErrorCode` (S1.2).

## Goals / Non-Goals

**Goals:**
- Первый вызов инструмента хода, не считая чтения skill, — `write_todos` в режимах `always` и `auto`.
- Ход без плана в `auto`; `off` — без ограничений.

**Non-Goals:**
- Качество плана и покрытие действий запроса (eval S5.1); доведение плана (S2.4).

## Decisions

### D1. Настройка режима

`AgentSettings.plan_mode: Literal["always", "auto", "off"] = "auto"` (`AGENT_PLAN_MODE`). Неверное значение — `ValidationError` pydantic с перечнем допустимых, как у `AGENT_ENGINE`. Строка в таблице README.

### D2. «План есть»

`bool(state.get("todos"))`. Отдельного флага нет: `write_todos` с пустым списком равносилен отсутствию плана, а план прошлого хода с `blocked` (его сохраняет `TurnContext`) считается планом хода (§8 п. 2: модель обновляет статусы, а не строит план заново).

### D3. `wrap_model_call` — сужение набора и повтор в `always`

Пока плана нет:
1. `request.override(tools=[t for t in request.tools if name(t) in {"write_todos", "read_file"}])`, `tool_choice` не трогается (`auto`).
2. `always`: если в ответе нет `tool_calls` — ответ отбрасывается, вызов повторяется один раз с `tool_choice="write_todos"` и тем же суженным набором. Первый ответ в состояние не попадает, поэтому последним сообщением промпта остаётся сообщение пользователя (S0.2). Если и повтор без вызова — его ответ возвращается как есть (ход не зацикливается).
3. `auto`: ответ без вызова возвращается как есть — ход без плана (FR-4).

С планом запрос проходит без изменений. ForcePlanFirst стоит после `TodoListMiddleware` (№10 → №11), то есть внутри неё: набор инструментов уже включает `write_todos`, а системный промпт — правила плана.

*Альтернатива:* `tool_choice="write_todos"` на первом вызове каждого хода (исходный ADR-3) — отвергнута spike S0.2: на ходах без расчёта модель выдумывает план. Принудительный вызов остаётся только повтором в `always`.

### D4. `wrap_tool_call` — `plan_required`

Пока плана нет, вызов разрешён, если это `write_todos` или `read_file` с путём (`file_path`, иначе `path`) внутри `/skills/`. Остальные вызовы не выполняются: возвращается `ToolMessage(to_json(failure(PLAN_REQUIRED)), tool_call_id, name, status="error")` — тот же конверт, что у адаптера (S1.2). Проверка действует в `always` и `auto` и страхует D3: модель может вызвать инструмент, которого нет в наборе (по памяти прошлых ходов), а скриптовая модель — несколько вызовов в одном ответе. Состояние при отклонении не меняется.

`ToolCallRequest.state` — состояние на момент перед узлом инструментов, поэтому `write_todos` и расчёт в одном ответе дают `plan_required` для расчёта. Для GigaChat (один вызов за ответ) это не встречается; принято.

### D5. Сборка

`AgentFactory(..., plan_mode=None)`: `None` → `APP_CONFIG.agent.plan_mode`. `ForcePlanFirst(mode)` добавляется сразу после `TodoListMiddleware`, если режим не `off`. Конструктор `ForcePlanFirst` отвергает `off` (`ValueError`): выключение — отсутствие middleware, а не ветка внутри.

### D6. Тесты

`ScriptedChatModel` пишет в журнал набор инструментов и `tool_choice` каждого вызова — по нему проверяются D3 и FR-3. Существующие сквозные сценарии (`test_runtime.TestTurn`, `test_turn_context` сквозной ход) получают первый шаг `write_todos`; так они заодно проверяют, что после плана расчёт выполняется.

## Risks / Trade-offs

- [В `auto` модель на запросе с расчётом отвечает текстом без плана и без цифр] → промпт `write_todos` требует плана для любого расчёта; доля таких ходов меряется eval S5.1; при плохом результате — режим `always`.
- [В `always` приветствие получает выдуманный план] → известно по S0.2, режим только для eval и отладки.
- [Сужение набора скрывает `resolve_terms` до плана] → так и задумано (FR-3); сопоставление идёт первым шагом плана (§8 п. 3).

## Migration Plan

Новый режим действует только в v2 (`AGENT_ENGINE=v2`). Откат поведения без изменения кода — `AGENT_PLAN_MODE=off`.

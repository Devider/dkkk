# Design

## Context

Мотивация — proposal.md, требования — `specs/agent-tools/spec.md`. Решения spike S0.3, на которые опирается story:
- термины вместо запроса не хуже исходного запроса (на 22 общих запросах: входы 82,9 % против 81,7 %, выходы 55,6 % против 41,7 %);
- Jaccard top-1 — 40 % (входы), у трети входов 0 → числовая оценка для решений не годится; согласие анализатора с Jaccard top-3 — точность 97,7 %, без согласия — 69,1 %;
- `AnalyzerSubAgent._resolve_names_internal` падает `KeyError: ''` на пустом ID (3–6 из 30 запросов) — теряется весь вызов;
- GigaChat отвечает 429 при параллельной нагрузке, клиент 429 не повторяет.

Устройство анализатора: `ainvoke(messages, available_inputs, available_outputs)` → `q_analysis` и `resolved_inputs`. Входы приходят с `equivalent_input_id`, выходы EMA (`QueryAnalysisEMA.mentioned_outputs`) — только с `equivalent_output_name`. Модель анализатора — `APP_CTX.llm`. Собирается из модулей смыслового слоя (`prompts.ema_analizer`, `prompts.lookup_more`, `states.agents`, `schemas.llm_outputs`, `subagents.analyzer`) — без `main_graph` (§7 п. 5).

Адаптер S1.1–S1.2 умеет только синхронные функции и не меняет состояние агента.

## Goals / Non-Goals

**Goals:**
- `resolve_terms` по решениям S0.3 поверх неизменённого смыслового слоя.
- Механизм обновления состояния из инструмента, пригодный и для других инструментов (`step_results`, S1.6).

**Non-Goals:**
- `ambiguous_term`: без измеренного критерия (близость оценок двух кандидатов) код не выставляется — после eval S5.1.
- Повышение точности анализатора.

## Decisions

### D1. Вызов анализатора

Один EMA-анализатор на процесс (`QueryAnalysisEMA` умеет несколько выходов и входов). Сообщение — как в R2 spike S0.3: «Сопоставь термины с моделью. Входные параметры: a; b. Выходные показатели: c.». Каталоги — `dict(index.inputs)`, `dict(index.outputs)`.

Сопоставление ответа с терминами: по `mentioned_input_name` / `mentioned_output_name` (без регистра и крайних пробелов), затем — по порядку среди ещё не сопоставленных терминов той же роли. Выход переводится в ID по точному совпадению имени в индексе; без совпадения — первый кандидат Jaccard среди выходов.

*Альтернатива:* IFT-анализатор для одного выхода — отвергнута: роль «одна цель» знает модель агента, а не инструмент.

### D2. Кандидаты, оценка, уверенность

Для каждого термина по его роли: `top = jaccard_top(normalize_text(term), имена роли, k=3)` (новый цикл в v2 поверх неизменённых `normalize_text` и `jaccard_similarity` — как в S0.3). Кандидаты: выбор анализатора (если есть) + до двух лучших из `top`, без повторов; `score` — Jaccard термина и имени, округлённый до 2 знаков. `confidence = high`, если выбор анализатора ∈ `top` с ненулевой оценкой, иначе `low` (уточнено при реализации: совпадение с именем нулевого сходства — это ничья, а не подтверждение). Нет выбора анализатора: кандидаты — `top` с ненулевой оценкой и `confidence: low`; все оценки нулевые → `term_not_found`.

### D3. Устойчивость

- Вызов анализатора по всем терминам; при исключении (в том числе `KeyError` из `_resolve_names_internal`) — по одному вызову на термин; термин, который и отдельно падает, остаётся без выбора анализатора (D2).
- `gigachat.exceptions.RateLimitError` → до 3 повторов с паузой 2, 4, 8 с (параметры — из `config/agent`: `AGENT_LLM_RETRY_ATTEMPTS`, `AGENT_LLM_RETRY_WAIT` уже есть).
- `StopEventError` не повторяется и проходит наружу (AR-Q11).

### D4. Асинхронный вызов и обновление состояния в адаптере

- `ToolSpec` получает необязательное поле `acall` — корутина вместо `call`; адаптер вызывает её без `to_thread`.
- `ToolSuccess` получает служебное поле `state_update: dict | None`, исключённое из JSON. Если оно есть, адаптер возвращает `Command(update={**state_update, "messages": [ToolMessage(json, tool_call_id=runtime.tool_call_id, name)]})` вместо строки.
- `api/v2/tools/state.py`: `ToolsState(AgentState)` с полем `resolved_terms: Annotated[dict, merge]` (редьюсер объединяет словари) — `CopilotAgentState` (S2.1) его расширит; пока каталог отдаёт его как `state_schema` для `create_agent` в тестах.

### D5. Конверт `resolve_terms`

`ToolSuccess.data = [{"text", "role", "status": "ok" | "term_not_found", "confidence", "candidates": [{"id", "name", "score"}]}]`; `result` — «Сопоставлено N из M терминов; с низкой уверенностью: …; не найдено: …»; `hint` — при `low` «сверь кандидатов по смыслу или переформулируй термин», при `term_not_found` — подсказка кода. `numbers` пуст (сопоставление чисел не даёт). Если не найден ни один термин — `ToolFailure(term_not_found)`.

### D6. Оценка точности

`scripts/eval/resolve_terms_accuracy.py`: та же выборка, что R1–R2 S0.3 (seed 42, 20 IFT + 10 EMA), термины — алиасы эталона, вызов `resolve_terms` через адаптер со скриптовым контекстом; метрика — доля правильных первых кандидатов против R1 v1 на запросах без падений. Последовательно, с повтором 429.

## Risks / Trade-offs

- [EMA-анализатор на терминах IFT-запросов не измерен отдельно] → скрипт D6 считает IFT и EMA раздельно; при просадке IFT — вернуться к выбору анализатора по роли.
- [Сопоставление ответа анализатора с терминами по имени может ошибаться при переформулировке] → запасной путь по порядку; тест на переставленные и переименованные термины.
- [Повторы и 429 увеличивают задержку хода] → лимиты хода и таймаут — S2.5, S2.8; один вызов на все термины в обычном случае.
- [`Command` из инструмента требует поля в схеме состояния] → `ToolsState` обязателен в `create_agent`; тест без него показывает понятную ошибку конфигурации.

Только `api/v2`, сервис его не вызывает. Откат — revert.

## Результаты

Прогон 2026-10-26, живой GigaChat (api_key, `GigaChat-3-Pro`), `scripts/eval/resolve_terms_accuracy.py`; отчёт — `scripts/eval/results/resolve_terms_20261026-121331.json`. Выборка — как R1–R2 spike S0.3 (seed 42, 20 IFT + 10 EMA); базовая линия v1 — прогон R1 spike.

| | `resolve_terms` | v1 (R1) |
| --- | --- | --- |
| Упавшие запросы | 0 из 30 | 3 из 30 |
| Входы, все запросы | 79,1 % (87/110) | 73,6 % (81/110) |
| Выходы, все запросы | 74,5 % (41/55) | 29,1 % (16/55) |
| Входы, 27 общих запросов | 78,0 % (78/100) | 81,0 % (81/100) |
| Выходы, 27 общих запросов | 77,3 % (34/44) | 36,4 % (16/44) |
| **Все параметры, 27 общих запросов** | **77,8 % (112/144)** | **67,4 % (97/144)** |

Уверенность: `high` — точность первого кандидата 100 % (n = 58), `low` — 68,3 % (n = 104); совпадает со spike S0.3 (97,7 % / 69,1 %).

**Решение разработчика (2026-10-26):** критерий FR-6 «не ниже v1» оценивается по всем параметрам — выполнен (+10,4 п. п.). Наблюдение для eval S5.1: по входам на общих запросах −3 п. п. (3 параметра из 100, в пределах разброса выборки); 5 из 6 ухудшившихся запросов — подбор под цель (IFT). Запасной путь — IFT-анализатор при одном выходном термине (риск D1) — не применялся.

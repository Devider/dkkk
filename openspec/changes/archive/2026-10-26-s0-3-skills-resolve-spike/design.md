# Design

## Context

Мотивация — proposal.md. Проверяемые решения: ADR-2 (skills и `/results/` из `deepagents`), ADR-4 (`resolve_terms` поверх смыслового слоя), ADR-7 (вынос больших результатов). Связанные места спецификации: §9 (состояние, `/results/`), §10 (контракт и каталог инструментов), §11 (skills и активация).

Текущее состояние (по коду, 2026-10-26; `deepagents` 0.7.29, `langchain` 1.4.6):
- `SkillsMiddleware(backend, sources, system_prompt, tools)`: каталог skills в системном промпте; `metadata.include_tools` во фронтматтере `SKILL.md` — инструмент виден только после `read_file` этого skill или его закрепления и пока чтение в контексте; закрепление — через ключ состояния `pinned_skills` во входе `invoke` (текст skill добавляется отдельным `HumanMessage`); предупреждения загрузки — в промпт (`{skills_load_warnings}`).
- `FilesystemMiddleware(backend, tools=[...], tool_token_limit_before_evict=20000)`: набор инструментов задаётся списком (можно только `read_file`); встроенный вынос результата инструмента длиннее порога (в токенах) в backend с превью и ссылкой.
- Backends: `CompositeBackend(default, routes)`, `StoreBackend(namespace=fn(runtime))`, `FilesystemBackend(root_dir, virtual_mode=True)` (документация предупреждает против использования в веб-серверах), `StateBackend`.
- `AnalyzerSubAgent.ainvoke(messages, available_inputs, available_outputs, user_id)` → `q_analysis` (`QueryAnalysisIFT` / `QueryAnalysisEMA`: цели, годы, диапазоны, `mentioned_inputs` с `equivalent_input_id`) и `resolved_inputs`. LLM видит весь каталог `INid → имя` в промпте и выбирает один ID на термин; при `lookup_more` — второй вызов. Оценок нет. Берёт модель из `APP_CTX.llm`.
- `find_matching_cell` / `find_matching_outputs`: Jaccard по `normalize_text` (стемминг), лучший вариант и `best_score` при `return_best_score=True`; порог 0,1. `tools.py` импортируется без LibreOffice, каталог строится через openpyxl (`subagents/utils.py:build_mappings`).
- Эталон: `tests/data/Methanex_tool_test_queries.xlsx` — по 300 запросов IFT и EMA; канонические имена входов и выходов, у IFT — алиасы из запроса (`input_aliases`).
- В `langchain_core` фейковые модели без `bind_tools` — `ScriptedChatModel` придётся писать.

## Goals / Non-Goals

**Goals:**
- Подтвердить или опровергнуть механику ADR-2 на `deepagents` 0.7.29 и выбрать, где лежат skills (каталог образа или store).
- Выбрать определение кандидатов и оценки для `resolve_terms` с измеренной точностью против v1, без правки смыслового слоя.
- Показать, что полный ход идёт на скриптовой модели без сети и LibreOffice (AR-Q2).

**Non-Goals:**
- Повышение точности матчера (вне рамок проекта, §2).
- Промышленный адаптер, конверт и коды ошибок (S1.1, S1.2).

## Decisions

### D1. Стенд вне приложения

`scripts/spikes/s0_3_skills_resolve/`: `run.py` (CLI `--checks`, JSON-отчёт), `scripted.py` (`ScriptedChatModel`), `skills_checks.py`, `resolve_checks.py`, `skills/` (тестовые skills), `README.md`. Модель для смыслового слоя — `APP_CTX.llm`, как в v1 (`AnalyzerSubAgent` берёт её сам). Расчёты движка — заглушка с фиксированной сеткой.

### D2. Проверки

| # | Что проверяем | Как | Критерий |
| --- | --- | --- | --- |
| K1 | `ScriptedChatModel` + `create_agent` | Сценарий: `write_todos` → `resolve_terms` (заглушка) → `run_scenarios` (заглушка) → ответ; ответы модели — функции от истории (берут ID из результата `resolve_terms`) | Ход завершается, в состоянии `todos`, вызовы в нужном порядке; ни одного сетевого вызова |
| K2 | Каталог skills и открытие инструмента | Тестовые skills `covenant-headroom` (`include_tools: calc_headroom`) и `economic-answer`; скриптовая модель вызывает `calc_headroom` до и после `read_file` | Каталог в системном промпте; до чтения — отказ «unknown tool», после — вызов проходит |
| K3 | Закрепление skill (`AGENT_PINNED_SKILLS`) | Вход `pinned_skills=["economic-answer"]` | Текст skill в контексте модели на каждом ходе; закреплённый `include_tools` виден без чтения |
| K4 | Только `read_file` | `FilesystemMiddleware(tools=["read_file"])` | В инструментах модели нет `write_file`, `edit_file`, `ls`, `glob`, `grep`, `execute`; вызов `write_file` отклоняется |
| K5 | Где лежат skills | (а) `FilesystemBackend(root_dir=skills, virtual_mode=True)` на маршруте `/skills/`; (б) skills загружены в store при старте, `StoreBackend` с общим пространством | Оба читаются; `read_file` за пределы `/skills/` (`../`, абсолютный путь к `.env`) в (а) отклоняется |
| K6 | `/results/` и изоляция | `StoreBackend(namespace=("results", user_id))` из runtime context; запись результата адаптером, чтение `read_file` моделью; второй пользователь с тем же `session_id` | Свой результат читается, чужой — нет |
| K7 | Встроенный вынос результата (ADR-7) | `tool_token_limit_before_evict` на малом пороге; маршрут, куда пишется вынесенный результат | Куда пишет (`artifacts_root`), в каком виде превью; можно ли направить в `/results/` пользователя и задать порог, близкий к 1500 символам |
| K8 | Невалидный skill (AR-Q15) | Skill без `description` / с битым фронтматтером | Как сообщает `SkillsMiddleware` (исключение или предупреждение в промпте) — нужна ли своя валидация при старте |
| K9 | GigaChat читает skill по описанию | Живой GigaChat, запрос под `covenant-headroom`, 3 прогона | Доля ходов, где модель сама вызвала `read_file` нужного skill |
| R1 | Базовая линия v1 | `AnalyzerSubAgent` (IFT / EMA) на исходном запросе, выборка из эталона | Per-param accuracy по входам и выходам |
| R2 | `resolve_terms` с терминами от агента | Тот же анализатор, но на вход — сообщение со списком терминов (алиасы из эталона), без исходного запроса | Accuracy против R1 |
| R3 | Jaccard top-k | Новый цикл в стенде по `normalize_text` + `jaccard_similarity` над каталогом для каждого алиаса | accuracy@1, @3; доля нулевых оценок; разделяет ли оценка верные и неверные |
| R4 | Комбинация | Кандидаты: выбор анализатора первым, затем Jaccard top-k; признак согласия (выбор анализатора в Jaccard top-3) | Точность выбора анализатора при согласии и без него — годится ли согласие как «низкая оценка» для FR-6 |

Выборка R1–R4: 20 запросов IFT и 10 EMA из эталона (≈ 120 параметров), фиксированный seed. Стоимость ≈ 60–90 вызовов GigaChat.

### D3. Критерии решений

- **ADR-2:** принимается, если K2–K4 и K6 проходят. По K5 выбирается хранение skills: каталог образа (если `virtual_mode` не выпускает за корень) или store (если выпускает или если так проще изоляция).
- **ADR-7:** если K7 позволяет направить вынос в `/results/` пользователя и задать порог — используется встроенный вынос, своя реализация в S1.6 не нужна; иначе остаётся своя, а встроенный отключается.
- **ADR-4:** `resolve_terms` принимает термины, если R2 не хуже R1 более чем на 5 п. п.; иначе принимает исходный запрос и роли терминов. Определение кандидатов и оценки — по R3 / R4: если согласие анализатора с Jaccard отделяет ошибки, оно и есть «низкая оценка»; если нет — оценка из Jaccard не используется для решений модели, и это фиксируется как отклонение от FR-6.
- **AR-Q15:** по K8 — нужна ли своя валидация skills при старте.

## Risks / Trade-offs

- [Эталон собран под v1 и содержит английские алиасы] → R3 занизит Jaccard; это и есть проверяемое свойство, вывод формулируется для такого распределения запросов.
- [Малая выборка] → разброс ±5–8 п. п.; решения D3 принимаются только при явном разрыве, иначе — консервативный вариант (исходный запрос, без оценки).
- [`AnalyzerSubAgent` поднимает `APP_CTX`] → импорт `aigw_service.context` в стенде допустим (без `on_startup`), как в тестах.

## Migration Plan

Не применяется: в приложение ничего не попадает. Стенд остаётся в `scripts/spikes/` до S5.4.

## Результаты

Прогон 2026-10-26: `deepagents` 0.7.29, `langchain` 1.4.6; K9 и R1–R2 — живой GigaChat (api_key, `GigaChat-3-Pro`). Отчёты — `scripts/spikes/s0_3_skills_resolve/results/`.

### Skills, `/results/`, скриптовая модель

| # | Итог | Что показал прогон |
| --- | --- | --- |
| K1 | ✓ | `ScriptedChatModel` (шаги — функции от истории) проводит ход `write_todos → resolve_terms → run_scenarios → write_todos → ответ` без сети; ID из результата `resolve_terms` попадают в аргументы расчёта; `todos` в состоянии |
| K2 | ✓ | Каталог skills в системном промпте. До `read_file` инструмент skill не виден модели, вызов → `"calc_headroom is not a valid tool"`; после чтения виден и работает |
| K3 | ✓, с оговоркой | `pinned_skills` во входе хода: текст skill в контексте, его `include_tools` видны без чтения. **Каждое закрепление добавляет новую копию**: на 2-м ходе в истории 2 копии |
| K4 | ✓ | `FilesystemMiddleware(tools=["read_file"])`: модель видит только `read_file`; `write_file` → «not a valid tool» |
| K5 | ✓ | Оба варианта работают: `FilesystemBackend(root_dir=skills, virtual_mode=True)` на `/skills/` отклоняет `../` («Path traversal not allowed»), чужие пути не находит; skills, загруженные в store при старте, тоже читаются |
| K6 | ✓ | `StoreBackend(namespace=("results", user_id))` из runtime context: свой результат читается, у второго пользователя с тем же `session_id` — «not found» |
| K7 | ✓, с оговорками | Встроенный вынос при `CompositeBackend(artifacts_root="/results/")` пишет в `/results/large_tool_results/<call_id>` в store пользователя, в `ToolMessage` — превью (~890 символов). Порог — в токенах; превью и подсказка — на английском; содержимое заменяется целиком |
| K8 | ✗ (нужна своя валидация) | Skill с битым фронтматтером молча пропускается: в каталоге его нет, только предупреждение в логе, исключения нет |
| K9 | 6/6 | GigaChat сам читает `covenant-headroom` по описанию и вызывает открывшийся `calc_headroom` — и с английским промптом skills по умолчанию, и с русским |

Попутно: встроенный `write_todos` знает только `pending` / `in_progress` / `completed` и не хранит причину — FR-5 (`skipped`, `blocked` с причиной) требует своей схемы.

### Смысловой слой (30 запросов эталона Methanex: 20 IFT + 10 EMA, seed 42)

| # | Входы | Выходы | Комментарий |
| --- | --- | --- | --- |
| R1 — v1, исходный запрос | 73,6 % (81/110) | 29,1 % (16/55) | 3 запроса из 30 упали целиком (`KeyError: ''`) |
| R2 — только термины | 66,4 % (73/110) | 45,5 % (25/55) | 6 запросов из 30 упали целиком |
| R1 / R2 на 22 общих запросах без падений | 81,7 % / 82,9 % | 41,7 % / 55,6 % | Термины не хуже исходного запроса |
| R3 — Jaccard по алиасу | @1 40 %, @3 48 % | @1 62 %, @3 76 % | Нулевая оценка у 32 % входов (английский алиас против русского имени); средняя оценка верного top-1 — 0,35, неверного — 0,13 |
| R4 — согласие анализатора с Jaccard top-3 | согласие: точность 97,7 % (n = 44); несогласие: 69,1 % (n = 55) | — | Согласие — сильный признак верного выбора |

- `KeyError: ''`: в `AnalyzerSubAgent._resolve_names_internal` пустой `equivalent_input_id` от LLM даёт `available_names['']` — падает весь вызов, а не один термин (дефект v1 в неизменяемом теле).
- При 3 параллельных запросах GigaChat отвечает 429 (14–17 из 30); клиент `gigachat` 429 сам не повторяет.
- Точность по выходам низкая и у v1 (EMA — 12,5 %); часть промахов может быть расхождением формулировок эталона — проверить при базовой линии S0.4.

### Решения

- **ADR-2 — принят.** Механика `SkillsMiddleware` + `FilesystemMiddleware(tools=["read_file"])` подтверждена (K2–K4, K6, K9). Skills хранятся в каталоге образа: `FilesystemBackend(root_dir=api/v2/skills, virtual_mode=True)` на маршруте `/skills/` — выход за корень отклоняется (K5), загрузка в store не нужна. `/results/` — `StoreBackend` с пространством `("results", user_id)` из runtime context.
- **Закрепление (`AGENT_PINNED_SKILLS`).** `TurnContext` передаёт в `pinned_skills` только те закреплённые skills, текста которых ещё нет в сообщениях сессии (после суммаризации — снова). Иначе копии копятся на каждом ходе (K3).
- **ADR-7 — своя реализация, встроенный вынос — страховка.** Встроенный вынос заменяет весь результат превью и обрезает `numbers`, нужные `AnswerGroundingGuard`, плюс англоязычный текст и порог в токенах. Поэтому адаптер (S1.6) сам пишет полный результат в `/results/<turn_id>/<call_id>.json` и оставляет в `ToolMessage` `result`, `numbers`, `ref`; встроенный вынос остаётся с высоким порогом на случай необёрнутых инструментов.
- **AR-Q15 — своя валидация skills при старте** (K8): фронтматтер, `name`, `description`, существование `include_tools`; ошибка останавливает старт.
- **FR-5 — своя схема плана:** `write_todos` со статусами `skipped` / `blocked` и полем `reason` (переопределение схемы `TodoListMiddleware`, S2.3 / S2.4).
- **ADR-4 — `resolve_terms` принимает термины** `[{text, role}]`, а не запрос: на общих запросах не хуже R1 (D3). Цели, годы и диапазоны модель передаёт в расчётные инструменты сама.
- **Кандидаты и оценка (отклонение от FR-6).** Числовая оценка сходства как основа решений не годится: Jaccard @1 — 40 %, у трети входов 0. Кандидаты: первым — выбор анализатора, затем Jaccard top-2 других имён с их оценкой (для справки). Решающий сигнал — `confidence`: `high`, если выбор анализатора входит в Jaccard top-3 (точность 97,7 %), иначе `low` (69,1 %). При `low` модель сверяет кандидатов по смыслу и переформулирует термин; вопрос пользователю — только если не может выбрать.
- **Устойчивость `resolve_terms`.** Адаптер ловит падение анализатора (`KeyError` на пустом ID) и повторяет вызов по одному термину; термин, который снова не разрешается, получает `term_not_found`. 429 повторяется с паузой: и вызовы смыслового слоя, и `ModelRetryMiddleware` должны повторять `RateLimitError`.

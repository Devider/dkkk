# Design

## Context

Пересчёт Excel-моделей идёт через headless LibreOffice (UNO/pyuno): каждый `ExcelWorkbook` поднимает свой `soffice` и открывает книгу in-memory ReadOnly. Сейчас после записи входных значений вызывается `doc.calculateAll()`. На «тяжёлых» моделях (ячейки `CHOOSE` с >30 аргументами, которые LO не читает) полный пересчёт валит их в `#VALUE!`, каскадно обнуляя выходы, обёрнутые в `IFERROR(...,0)`. Мотивация и симптом — см. `proposal.md` → Why. Здесь фокус на том, как именно перейти на инкрементальный пересчёт и как корректно докладывать о непосчитанных выходах.

Ограничения текущей реализации (constraints):
- `CalcBook` в `lo_backend.py` уже читает признак ошибки ячейки (`cell.getError()`) в `_scalar()` и возвращает ошибку как строку — но только в `get_value()` (по-ячеечно).
- `get_compiled_func()` в `excel_handler.py` проталкивает входы и считывает выходы одним `getDataArray` на лист; для ошибки формулы `getDataArray` возвращает `None` (а не текст), поэтому различие «ошибка vs пусто» в bulk-пути не теряется только после точечной допроверки (см. D2).
- `tools.py` формирует результат инструмента `ExcelAnalysisToolResult.content`.
- `models/06.10.2026.bak.xlsx` — «поломаная» (регрессия), `.xlsx`/`.fixed.xlsx` — исправленные (эталон).

## Goals / Non-Goals

**Goals:**
- Сделать инкрементальный пересчёт (`doc.calculate()`) основным на всех этапах конвейера, сохранив полный `calculateAll()` как отладочный вызов.
- Сделать так, чтобы «поломаные» модели (нечитаемые ячейки вне изменяемой цепочки) считались в числа, как в Excel.
- Научить тулы явно сообщать о непосчитанных выходах (в `content`), различая ошибку формулы и легитимный `0`/`None`.
- Не менять внешний HTTP-контракт.

**Non-Goals:**
- Патч/обход `CHOOSE`-формул в памяти для случая, когда тяжёлая ячейка сама в «грязной» цепочке (отдельная задача).
- Изменение name-resolution, HTTP-контракта, формата всего ответа тула, устаревших тестов `test_tools_performance.py`.
- CLI-флаг/постоянный fallback для полного `calculateAll()`.

## Decisions

### D1. Основной режим — инкрементальный `doc.calculate()`

`CalcBook.calculate()` делегирует в `self.doc.calculate()` (пересчёт только «грязных» зависимостей). Все три точки конвейера (`ExcelWorkbook._open()`, `ExcelWorkbook.calculate()`, `get_compiled_func().evaluate()`) вызывают `calculate()` вместо `calculate_all()`.

**Почему**: `calculate()` повторяет поведение Excel/десктопного LO и не трогает неиспользуемые нечитаемые ячейки, поэтому «поломаные» модели считаются корректно (эксперимент: `set AJ14=80` без `calculateAll` → `O70=27.43`). `calculateAll()` пересчитывает всю книгу, включая ломающиеся ячейки. Также `calculate()` быстрее (пересчёт только затронутого подграфа).

**Альтернативы рассмотрены**: оставить `calculateAll()` — отклонено (ломает тяжёлые модели); делать оба вызова — избыточно и дорого. `calculateAll()` сохраняется как метод `calculate_all()` для явного/отладочного использования, вне обычного пути.

### D2. Различение причины непросчёта — гибрид «bulk `getDataArray` + точечная допроверка через `_scalar`»

**Экспериментально подтверждено** (живой мост, LO 25.2.x; `read_block` vs `get_value` после `calculate_all()`):

| ячейка | `get_value` (`_scalar`, `getError`) | `read_block` (`getDataArray`) |
|---|---|---|
| `=1/0` → `#ДЕЛ/0!` | `'#ДЕЛ/0!'` (str) | `None` |
| `="a"*2` → `#ЗНАЧ!` | `'#ЗНАЧ!'` (str) | `None` |
| `=NA()` → `#Н/Д` | `'#Н/Д'` (str) | `None` |
| `=3`, `=0`, `=IFERROR(1/0,0)` | число | число |
| пустая | `None` | `None` |

**Ключевой факт**: `getDataArray` (`read_block`) возвращает **`None`** и для ошибки формулы, и для пустой ячейки — текст ошибки (например `#ЗНАЧ!`) приходит только из `_scalar()` через `cell.getError()`. То есть в горячем пути `evaluate()` оба случая сейчас неразличимы.

`CalcBook._scalar()` уже возвращает строку ошибки (`cell.getString()`) при `cell.getError() != 0` — это и есть надежный признак. Чтобы не терять его в bulk-чтении, признак ошибки **доносится наружу гибридно**:

1. `read_block()` → `getDataArray()` остаётся bulk-чтением для групп по листу (главная оптимизация, см. D1/Docstring `get_compiled_func`), как сейчас.
2. В `get_compiled_func().evaluate()` для каждой ячейки, у которой bulk вернул `None` (подозрительно: пустая **или** ошибка), выполняется **точечная допроверка** `book.get_value(sheet, row, col)` → `_scalar()`. Если это ошибка формулы, `_scalar` вернёт строку `#ЗНАЧ!`/`#ДЕЛ/0!`/`#Н/Д` и т.п.; пустая вернёт `None`.
3. В результате `evaluate()` отдаёт для каждого выхода: `float` (легитимный результат), `str#...!` (ошибка формулы), `None` (пусто/непосчитано) — три различимые категории.

**Границы ответственности:** **различение** этих категорий производит движок (`evaluate()` после гибридного проброса); `tools.py` **только классифицирует** уже различимые значения в «непосчитанные» и строит уведомление, не переизобретая различение на уровне движка (см. spec «Явное уведомление»).

**Почему именно так**: обычный случай (выход посчитан числом) не дёргает `get_value` — один `getDataArray` на лист, производительность не регрессирует. Точечная допроверка идёт только для `None`-ячеек, которых в норме мало (единичный over-head IPC), и даёт различие «ошибка формулы» vs «пусто», требуемое спекой. Проброс без изменения bulk-пути невозможен (см. таблицу: `getDataArray` теряет различие), поэтому `getError` читается по-ячеечно в подозрительных случаях.

**Альтернативы рассмотрены**:
- *Формализовать строку-ошибку из `getDataArray`* (префикс `#…!`) — **отклонено экспериментально**: `getDataArray` возвращает для ошибки `None`, а не текст, предикату нечего ловить.
- *Читать все выходы через `_scalar()` по-ячеечно (Вариант B)* — отклонено: ломает батчинг `getDataArray` и дорого на больших сценариях.
- *Не различать (считать любой `0`/`None` потенциально непосчитанным)* — отклонено, даёт ложные срабатывания на легитимных нулях и пустых ячейках.

**Классификация на уровне `tools.py` (Вариант 4, см. spec «Явное уведомление»):** непосчитанный выход = «ошибка формулы» (`str#…!`) ИЛИ «пусто/непосчитано» (`None`); `0.0` считается легитимным и в уведомление не попадает. **Распознанное ограничение:** если выходная ячейка обёрнута в `IFERROR(...,0)`, а источник ошибки — в её зависимостях, движок возвращает `0.0`, который на уровне значения выхода неотличим от честного нуля; именно так баг-сценарий `calculateAll()` маскировался как `0.0`. При `calculate()` (основной режим) этот каскад в норме не возникает; если же грязная тяжёлая ячейка попадёт в путь входа и выход снова сойдётся в `0.0`, инструмент вернёт его как легитимный ноль — выявление таких случаев по графу зависимостей является **отдельной задачей** (вне скоупа, см. Non-Goals / Risks).

### D3. Уведомление — только поле в `content`, только при наличии проблем

Информация о непосчитанных выходах добавляется **только** внутрь `ExcelAnalysisToolResult.content`, и **только когда** есть непосчитанные выходы (при полном успехе — ничего). Внешний HTTP-контракт не меняется.

**Почему**: минимальный след в контракте; отчёт пишется только по факту проблем — не захламляет успешные ответы.

**Альтернатива**: отдельное поле на уровне HTTP-ответа или отдельный warning-канал — отклонено (меняет контракт / лишний канал).

## Risks / Trade-offs

- **[Риск]** Грязная тяжёлая `CHOOSE`-ячейка на пути меняемого входа: `calculate()` пересчитает её → `#VALUE!` снова → выход непосчитан. → **Митигация**: не решается инкрементальным пересчётом; это отдельная задача (патч формул в памяти). В рамках дельты тул уведомит о непосчитанном через требование «Явное уведомление» — для случаев, когда выход сходит в `None`/`#…!`; **если же выход маскируется `IFERROR(...,0)` в `0.0`, тул вернёт легитимный ноль и не отметит** (известное отклонение, см. D2; выявление по графу — отдельная задача).
- **[Риск]** Volatile-функции (`TODAY`/`NOW`/`RAND`) и внешние ссылки могут не подхватиться инкрементальным пересчётом. → **Митигация**: это ровно поведение Excel; отладочный `calculate_all()` остаётся для диагностики.
- **[Риск]** Гибридный проброс признака ошибки (точечная допроверка `None`-ячеек в `evaluate`) добавляет по одному IPC-чтению на подозрительную ячейку и задевает семантику `content`. → **Митигация**: допроверка только для `None`-ячеек (в норме их мало); добавление только поля о непосчитанных, без изменения остальных полей; покрыть тестами.
- **[Риск]** openpyxl в обычном режиме не открывает «поломанные» файлы (падение `datavalidation`/`MultiCellRange`). → **Митигация**: читается `read_only=True`; каталог книги строится read-only; это вспомогательный риск, вне скоупа дельты, зафиксирован в intent.

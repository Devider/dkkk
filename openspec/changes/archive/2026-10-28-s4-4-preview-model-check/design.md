# Design: S4.4 — A/B-проверка preview-модели в middleware

Мотивация и рамки — proposal.md. Требования — `specs/agent-platform/spec.md` (ADR-10, AR-Q5). Решения опираются на ADR-10 и результат spike S0.2 C9 (`archive/2026-10-26-s0-2-gigachat-agent-spike/design.md`).

## Context

- v1: `core/llm_executor.Agent(GigaChat)` переопределяет `invoke` / `ainvoke` / `bind_tools`, кладёт `(result, args, kwargs)` в `asyncio.Queue` без предела, а фоновая задача (`start_background_worker` из `AppContext.on_startup`) повторяет вызов на `<model>-preview` и вызывает судью `_llm_judge` с промптом «оцени схожесть 0–100». Сравниваются `str()` ответов. Сбой preview-модели роняет фоновую задачу: исключения в `_process_background_checks` не ловятся.
- v2: `models.build_model()` возвращает обычный `GigaChat`. `AgentFactory.middleware()` задаёт порядок стека, `ContextMeter` — самый внутренний `wrap_model_call`. Он видит запрос в том виде, в каком его получает модель.
- `create_agent` сам связывает модель с запросом (`factory._get_bound_model`): без `response_format` это `request.model.bind_tools(request.tools, tool_choice=request.tool_choice, **request.model_settings)`, затем вызов на `[system_message, *messages]`. Агент v2 `response_format` не использует.
- Сервис вызывает агента только через `ainvoke` (`api/v2/service.py`). Синхронный путь есть лишь в отдельных тестах.
- Spike C9: накладные расходы прототипа в `wrap_model_call` — 0,02 мс. Preview-модели на `api.giga.chat` нет (404), она есть только во внутреннем контуре.

## Goals / Non-Goals

**Goals:**
- Одна проверка на логический вызов модели агента, по точному запросу этого вызова.
- Ни ответ, ни время хода от проверки не зависят. Любой сбой проверки остаётся внутри фонового обработчика.
- Итог проверки — машиночитаемая строка журнала, пригодная для разбора скриптом.

**Non-Goals:**
- Общий с v1 код: v1 и v2 не импортируют друг друга, подкласс `Agent` остаётся как есть до S5.4.
- Гарантия доставки проверок: при перезапуске сервиса или переполнении очереди проверки теряются. Это выборочная диагностика, а не учёт.

## Decisions

### D1. Место в стеке — перед `ContextMeter`, а не №6 из §8 (отклонение)

§8 ставит `PreviewModelCheck` шестым, сразу после `Telemetry`. Но `wrap_*` вложены: всё, что ниже в списке, меняет запрос уже после него. На месте №6 middleware увидел бы запрос до сжатия истории (`SummarizationMiddleware`, №7), без каталога skills (№8), без промпта плана (№10) и без фильтра инструментов `ForcePlanFirst` (№11). Preview-модель получила бы другой запрос, и сравнение было бы нечестным. Довод ADR-10 «middleware видит весь запрос» выполняется только у самого внутреннего обёртывателя.

Решение: `PreviewModelCheck` стоит вторым с конца, сразу перед `ContextMeter`. `ContextMeter` остаётся самым внутренним, оба видят один и тот же запрос, потому что ни один из них его не меняет. Побочный плюс: на этом месте middleware уже внутри `ModelRetryMiddleware` (№14). Неудачные попытки до него доходят исключением, а проверка ставится только по успешному ответу, поэтому на логический вызов — одна проверка, даже с повторами.

Альтернатива — №6 с пересборкой финального запроса внутри middleware. Отклонена: пришлось бы повторять логику пяти чужих middleware. §8 №6 обновляется в спецификации проекта.

### D2. Фоновый обработчик: ограниченная очередь и одна задача на event loop

- `PreviewChecker` владеет `asyncio.Queue(maxsize=PREVIEW_QUEUE_SIZE)` (константа 50) и одной задачей-обработчиком. Задача создаётся лениво, при первой постановке в очередь, в текущем event loop. Если loop сменился (тесты), создаётся новая очередь и новая задача. Задача создаётся с пустым контекстом: `asyncio.create_task(..., context=contextvars.Context())`. Иначе она унаследует contextvars хода, в котором создана, в том числе родительский run LangChain, и все последующие проверки попадут в дерево трассы первого хода.
- Постановка — `put_nowait`. При `QueueFull` проверка отбрасывается, пишется `PREVIEW CHECK` с `error="queue_full"`. Ход не ждёт никогда.
- Проверки выполняются по одной: preview-модель не нагружается параллельно с основным трафиком сильнее, чем один дополнительный поток вызовов.
- Обработчик ловит любое исключение одной проверки (`except Exception`) и пишет код. Задача не умирает, в отличие от v1. `CancelledError` пропускается наружу.
- `shutdown()` отменяет задачу, ждёт её и очищает очередь. Модульная `default_preview_checker()` (как `default_gate()`) вызывается из `lifespan` после `APP_CTX.on_shutdown()`. Пока задача не создана, вызов ничего не делает, на v1 тоже.

Альтернатива — `asyncio.create_task` на каждую проверку. Отклонена: нет предела на число одновременных вызовов preview-модели и нечего гасить при остановке.

### D3. Что кладётся в очередь и как вызывается preview-модель

В очередь кладётся неизменяемый снимок: `system_message`, копия списка `messages`, `tools`, `tool_choice`, `model_settings`, ответ основной модели (`AIMessage`) и метаданные — `trace_id` из `runtime.context`, `turn_id` из состояния, номер вызова `call_number(state)` из `context_meter`. `state` и `runtime` целиком не сохраняются: они живут дольше хода и меняются.

Обработчик вызывает `preview.bind_tools(tools, tool_choice=tool_choice, **model_settings).ainvoke([system_message, *messages], config={"callbacks": []})`. Это повторяет связывание `create_agent` (Context). Пустой список callbacks отрезает вызов от callback-handler'а Langfuse хода: вызов не попадает в дерево хода и не пишет `LLM CALL`. Без инструментов (`tools` пуст) — `bind(**model_settings)`. Повторов нет: у preview-модели собственный `GigaChat` без `ModelRetryMiddleware`.

Почему не `handler(request.override(model=preview))`: handler — замыкание текущего вызова графа. После ответа он может быть уже недействителен, и он внутри ретраев и телеметрии хода.

### D4. Модели: preview строится рядом с основной, судья — основная модель

`models.build_preview_model()` возвращает `GigaChat(**APP_CONFIG.gigachat.base_params, model=f"{APP_CONFIG.gigachat.model}-preview")` — то же правило имени, что в v1. Судья — отдельный экземпляр `GigaChat` основной модели без инструментов. Это не модель агента: вызов судьи не проходит через стек и не учитывается в лимитах.

`AgentFactory` получает необязательный `preview_check: PreviewModelCheck | None`. `None` — решать по настройкам: ставится, только если `AGENT_PREVIEW_CHECK=true` и `AGENT_MODEL=gigachat`. При `scripted` пишется предупреждение и проверка не ставится. Тесты передают `PreviewModelCheck` со скриптовыми или фейковыми preview-моделью и судьёй и RNG с фиксированным результатом.

### D5. Сравнение: детерминированно для вызовов, судья для текста

Решение пользователя:
- Если хотя бы одна модель вызвала инструменты: `same_tools` — совпадают упорядоченные списки имён, `same_args` — совпадают пары (имя, аргументы) после `json.dumps(sort_keys=True)`. Судья не вызывается, `similarity = null`.
- Если обе ответили текстом: судья с русским промптом в духе v1 («Сравни два ответа… Итоговый процент схожести: <число>%»). Оценка разбирается регулярным выражением и ограничивается 0–100. Не разобрано → `similarity = null`, `error = "judge_unparsed"`. Сбой вызова → `error = "judge_failed"`.
- Ошибка preview-модели: `error = "preview_failed"`, StopEvent — `"stop_event"`. Ошибки кодами, без текста исключения (FR-14). Тип исключения пишется в поле `exception` — как в `Telemetry`.

### D6. Строка журнала

`logger.info("PREVIEW CHECK {}", json.dumps(record, ensure_ascii=False))`, где `record` — `trace_id`, `turn_id`, `call`, `model`, `preview_model`, `elapsed_s` (preview + судья), `main` и `preview` — каждый `{"tool_calls": [{"name", "args"}], "text": <первые 1000 символов>}`, `same_tools`, `same_args`, `similarity`, `judge` (анализ судьи, первые 500 символов), `error`, `exception`. Формат JSON после маркера — как у `LLM CALL` / `TOOL CALL`, чтобы разбирать одним способом. Тексты ответов в журнал уже пишет v1, так что новых данных в журнале не появляется.

### D7. Выборка и синхронный путь

- `random() < percent`: при `percent=0` проверок нет, при `1` — каждая. RNG — параметр конструктора (по умолчанию `random.random`), тесты подставляют свой.
- `wrap_model_call` (синхронный) просто вызывает `handler`: фонового loop там нет, а сервис идёт асинхронно. Это записано в docstring и в «Вне рамок» proposal.

### D8. Конфигурация

`AgentSettings.preview_check: bool` (`AGENT_PREVIEW_CHECK`, `False`) и `preview_check_percent: float` (`AGENT_PREVIEW_CHECK_PERCENT`, `0.05`, `ge=0, le=1`). Переменные v1 в `config/app` не трогаются и на v2 не влияют. Решение пользователя: v1 и v2 включаются независимо, как требует AR-Q5.

## Risks / Trade-offs

- [Проверки расходуют квоту GigaChat под теми же учётными данными; 429 основной модели станет чаще] → по умолчанию выключено; доля 0.05; проверки идут по одной (D2).
- [Снимок держит в памяти копию сообщений до 50 запросов] → предел очереди; при 30 000 токенов на запрос это единицы мегабайт.
- [Обработчик работает в том же event loop, что и ходы; долгий разбор ответа мог бы занять loop] → разбор — несколько `json.dumps` и регулярное выражение; сетевые вызовы асинхронные.
- [Отличие от §8 №6 (D1)] → спецификация проекта обновляется в этой story.
- [Preview-модели вне контура нет: на `api.giga.chat` каждая проверка даёт `preview_failed`] → живая проверка только в контуре (эпик 5); юнит-тесты на фейковых моделях.
- [`json.dumps` аргументов с числами float может различаться в последнем знаке у двух моделей] → это реальное различие аргументов, а не шум: `same_args=false` — верный итог.

## Migration Plan

- Развёртывание: без переменных ничего не меняется. Включение в контуре — `AGENT_PREVIEW_CHECK=true` и перезапуск. Откат — убрать переменную.
- v1 продолжает использовать `ENABLE_PREVIEW_MODEL_CHECK`. Обе проверки можно включить одновременно, они не пересекаются.

## Open Questions

- Нужна ли отдельная переменная для имени preview-модели, если в контуре имя будет не `<модель>-preview`. Сейчас — правило v1; станет ясно при живом прогоне в контуре.
